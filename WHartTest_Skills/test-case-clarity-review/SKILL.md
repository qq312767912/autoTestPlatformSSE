# 测试用例清晰度审查

把测试用例当作可独立执行、可复现、可判定的验收说明进行审查。

1. 识别前置条件、测试数据、操作步骤和预期结果的缺失。
2. 检查步骤和可观察结果是否对应，最终业务结果是否被验证。
3. 区分确定缺陷、待业务确认和优化建议。
4. 保留源 Sheet、行号、用例编号、模块、原优先级，以及原用例的前置条件、步骤和预期原文，保证测试人员可在同一行复核，不必反复切换源文件。
5. 不凭空补造未知业务规则；无法确定的标准标记为“待业务确认”。
6. 高风险问题必须经过语义复核，不能仅按关键词机械定级。
7. 对每条问题给出可供测试人员直接参考的“修改示例”：结合该用例原文，拟写对应的前置条件、步骤和预期结果；尽量形成完整、可执行、可判定的改写，不要只重复“修改建议”。必须严格分成“前置：… / 步骤：… / 预期：…”三段，段落之间空一行；步骤和预期逐行编号。相对原文新增或改写的最小连续文本片段用 `【改】…【/改】` 包住，未变化原文不加标记；标记必须成对且不得嵌套，报告生成时会移除标记并将其中内容着色突出。需求或业务规则不足以支持具体结论时，用“【待业务确认：…】”标出缺失信息，不得自行编造。确实无需改写时才留空。
8. 涉及异步发送、回调、状态报告、批处理或同一业务对象被多个任务复用时，必须检查状态关联键与数据隔离覆盖。若用例只验证单任务或单批次，未覆盖“相同手机号/账号/对象同时存在于不同会议、任务或批次，且各自回调结果不同、到达顺序不同”的场景，应指出跨任务串改风险。先后发起任务不等于状态已处理完成；必须覆盖前一任务的延迟回调在后一任务记录创建后才到达的场景，并按 `references/review-rules.md` 中的“跨任务与跨批次状态隔离”规则给出补充用例示例。

## 报告人工确认与统计

Excel 报告的“问题明细”必须在审查字段后附加四个空白的人工处理字段：

- `问题确认`：仅允许测试人员选择“是”或“否”，初始为空。
- `问题描述`：由测试人员记录确认后的问题描述，初始为空。
- `修改点`：由测试人员记录实际修改内容，初始为空。
- `不采纳原因`：选择“否”时记录原因，初始为空。

“问题明细”中，“模块”后紧接 `原优先级` 与 `原文（前置/步骤/预期）`。原文按“前置：… / 步骤：… / 预期：…”分段，完整保留源用例对应单元格内容；源文件没有该字段时明确写“（原表未提供）”。`修改示例` 紧跟在 `修改建议` 后面，由 AI 按上方规则拟写，且按前置/步骤/预期分段；导出时移除 `【改】`、`【/改】` 控制标记并将标记内文字设为红色加粗下划线，不能与人工填写的 `修改点` 混淆；原有“改写示例”工作表继续保留相同的分段和高亮。长内容应自动换行并给足列宽和行高，人工确认字段仍保持空白、可筛选和可编辑。

报告必须增加红色页签的“测试确认处理结果”工作表，使用 Excel 公式关联“问题明细”的人工选择，不得把统计结果写死。至少包含：

- 总体统计：共审查用例数、审查提供意见数、采纳数、不采纳数、待确认数、采纳率。
- 按问题类型分布：每类问题的意见数、采纳数、不采纳数、待确认数和采纳率。
- 采纳率定义为“采纳数 ÷ 审查提供意见数”；没有审查意见时显示 0%。

严重程度：高表示核心错误仍可能被判定通过；中表示不同执行人可能得出不同结论或遗漏重要边界；低表示主要影响效率、维护与证据追溯。
