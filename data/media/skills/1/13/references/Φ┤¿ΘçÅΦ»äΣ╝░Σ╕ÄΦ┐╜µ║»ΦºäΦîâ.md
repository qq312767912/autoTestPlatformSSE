# 测试方案质量评估与追溯规范

本规范用于 Step1 原子需求抽取、Step2 测试点生成、AI结构自检和人工评审后指标计算。它不替代本次需求事实；任何固定规则与本次需求冲突时，必须以本次需求为准并保留冲突记录。

## 1. 事实来源优先级

从高到低：

1. 本次需求正文、表格和本次需求图片中的明确标注；
2. 本次产品、开发、测试确认结论；
3. 本次附件、数据字典、接口文档、原型和输出样例；
4. 当前页面感知结果；
5. 当前知识库中与本模块匹配且可定位来源的规则；
6. 本次已评审人工方案或用例；
7. AI通用测试经验。

低优先级来源不得静默覆盖高优先级来源。出现阈值、等号方向、字段数、枚举值、文案或流程冲突时，写入 `冲突清单.xlsx`，相关测试点标记 `待确认`。

## 2. 原子需求结构

`原子需求清单.xlsx` 每行一条原子需求，包含需求ID、系统/模块、需求描述、验收规则、优先级、来源类型、来源文件或知识条目、来源定位、确认状态、人工意见、覆盖评审和完整性评审。

`source_type` 取值：`document_text`、`document_table`、`document_image`、`attachment`、`confirmed_decision`、`historical_plan`、`domain_rule`。

图片必须先完成识别和人工确认，再作为 `document_image` 来源。保留图片ID、页码、所属模块和确认后的结构化内容；不能只记录 OCR 全文。

图片内部采用以下证据规则：

1. 视觉AI结构化结果是图片内容的主证据；结果完整、语义连贯且无明显异常时直接采用。
2. OCR是兜底证据，只在视觉AI解析失败、缺失关键内容或明确低置信度时使用。
3. OCR漏字、乱码、表格错位以及OCR与可靠视觉AI结果不一致，只记录为内部识别质量问题，不进入 `冲突清单.xlsx`。
4. 视觉AI本身不确定，或视觉AI提取出的业务事实与正文、表格、附件、确认结论或知识库明确规则不一致时，才生成待确认或业务冲突。

## 3. 原子化规则

- 一个需求只表达一个可验证目标；“查询功能正确”必须拆成开始日期、结束日期、日期组合、状态、日期+状态、默认排序等独立需求。
- 阈值必须保留运算符，例如 `>90`、`<=90`、`<40`、`>=40`，不得改写成“高分/低分”。
- 枚举每个值、状态流转每条边、列表每组字段、失败继续/中止语义分别形成原子需求。
- 图片中的新增按钮、查询项、列表列、状态、提示语和标注区域都要原子化。
- 原文含“正确、正常、合理、符合预期”但未给出口径时，标记 `needs_clarification`，不得自行补成业务事实。

## 4. 覆盖矩阵

在 `测试方案.xlsx` 的“需求覆盖关系”工作表中，每行一个原子需求，记录关联测试点、场景类型、关联缺口、待确认原因和人工覆盖评审。

P0/P1 原子需求不得无测试点。需要多场景验证的规则，必须按适用性覆盖正向、反向、边界、异常或组合场景；不适用时写明原因。

## 5. 测试点来源分类

- `requirement`：本次需求明确要求；计入需求覆盖率。
- `knowledge_base`：当前知识库补充；必须带来源并确认未与本次需求冲突。
- `page_state`：当前页面感知结果；用于识别测试对象和实现差异，不能覆盖需求预期。
- `ai_extension`：安全、兼容、性能、并发等经验性补充；单独展示，不得冒充本次需求，也不得默认设为高优先级。

## 6. 八项核心指标

八项指标是评估AI能力的结果指标，不是AI生成时的自检项。AI不能判断自己是否理解正确、是否真正覆盖需求、是否可被人工直接接受，也不知道人工最终补充或删除了什么。因此必须先产生人工评审数据，再由平台按公式计算。

| 指标 | 计算方式 |
| --- | --- |
| 需求覆盖率 | 已被测试点覆盖的原子需求数 / 原子需求总数 |
| 测试点准确率 | 业务含义正确的 AI 测试点数 / AI 测试点总数 |
| 测试点完整率 | 场景拆分完整的需求数 / 需要多场景验证的需求总数 |
| 测试点可追溯率 | 具有有效需求ID和来源定位的测试点数 / AI 测试点总数 |
| 人工直接接收率 | 未经实质修改直接接受的 AI 测试点数 / AI 测试点总数 |
| 人工补充率 | 人工新增测试点数 / 最终确认测试点总数 |
| 无效测试点率 | 被人工删除的 AI 测试点数 / AI 测试点总数 |
| 测试点重复率 | 被判定为重复的 AI 测试点数 / AI 测试点总数 |

建议人工评审记录：

- 原子需求：`covered/uncovered`、`complete/incomplete/not_applicable`；
- AI测试点：`accepted/minor_edit/major_edit/deleted/duplicate`；
- 人工新增测试点：`human_add`；
- 规则冲突：`resolved/unresolved`。

没有上述评审记录时，八项指标均不得输出得分，也不能用AI自己建立的关联关系替代人工结论。

## 7. AI生成阶段结构自检

AI可以执行但不得称为质量评分的检查：

- 是否有原子需求没有关联任何测试点；这只是“关联缺口”，不是已验证的需求覆盖率；
- 测试点是否缺少需求ID或来源定位；
- 是否存在未解决规则冲突；
- 是否存在文本高度相似的疑似重复点；
- 是否存在只有“验证正确/展示正常/符合预期”而没有明确预期的表述；
- `ai_extension` 是否与需求测试点分区展示。

输出文件为 `生成结构自检.xlsx`，必须标明“仅为AI结构自检，不能作为八项指标结果”。

## 8. 人工评审后计算

人工完成标注后，平台或确定性脚本根据评审记录生成 `AI质量评估结果.xlsx`。目标值可用于版本验收或模型/skill迭代对比，但不阻止AI生成草稿。指标结果必须同时保存分子、分母、样本版本和评审人/评审批次，避免只有百分比而无法复核。

所有需要人工审核、确认或回填的产物必须是Excel。JSON只能作为平台内部中间态。
