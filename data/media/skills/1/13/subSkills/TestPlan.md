# Step2 通用测试方案生成

## 输入

- 经人工检查或回填后的 `原子需求清单.xlsx`；
- `冲突清单.xlsx`；
- 用户提供的历史方案或输出模板（可选）；
- 当前项目测试策略和环境信息（来自知识库或用户输入）。

默认使用 `templates/test_plan_template.xlsx` 的公司格式；用户提供更新版时对齐更新版。模板只约束格式，不提供本次业务事实。

## 生成原则

1. 先按原子需求动态归类模块，不使用固定模块数量或固定功能名称。
2. 根据需求类型选择测试方法，见 `references/通用测试设计规范.md`。
3. `requirement`、`knowledge_base`、`page_state` 和 `ai_extension` 分开标识。
4. 冲突未解决时生成候选测试点并标记 `needs_clarification`，不得选定一个口径。
5. 不为追求数量机械生成安全、兼容、性能、边界或异常测试。

## 测试方案.xlsx

至少包含以下工作表：

### 1. 测试方案

项目/系统、需求或版本、输入资料、测试目标、范围、范围外、策略、环境、数据、资源、里程碑、风险和待确认事项。所有名称和环境动态获取。

不得写“覆盖率100%”。可以写事实数量，例如“共关联X条原子需求，仍有Y条待人工确认”。

### 2. 测试方案明细

| 列 | 说明 |
| --- | --- |
| 方案编号 | 稳定唯一 |
| 系统/模块 | 动态识别 |
| 测试场景类型 | 功能、边界、异常、状态、权限、接口、数据等 |
| 测试场景 | 场景名称 |
| 测试要点 | 条件、操作和明确预期 |
| 优先级 | P0/P1/P2或项目定义 |
| 原子需求ID | 一个或多个 |
| 来源类型 | 与原子需求一致 |
| 来源定位 | 可审计来源 |
| 确认状态 | confirmed / needs_clarification |
| 备注 | 数据、环境、依赖 |
| 人工评审状态 | accepted / minor_edit / major_edit / deleted / duplicate |
| 人工修改意见 | 人工填写 |

### 3. 需求覆盖关系

每行一个原子需求，列出关联测试点编号、关联场景类型、是否存在关联缺口、待确认原因和人工覆盖评审。

AI只能判断“是否建立关联”，不能判断真实覆盖。列名使用“关联状态”，不能使用“AI覆盖率”。

### 4. 待确认项

从冲突清单和原子需求同步所有 `needs_clarification` 项，包含影响测试点。人工确认后重新生成或更新相关测试点。

## 结构自检

调用 `scripts/plan_quality_validator.py --mode self-check` 输出 `生成结构自检.xlsx`，检查原子需求无测试点关联、测试点无需求ID或来源、引用不存在的需求ID、未解决冲突、疑似重复和空泛预期。

这不是八项指标评分。人工完成评审后，才可以用 `--mode reviewed` 生成 `AI质量评估结果.xlsx`。
