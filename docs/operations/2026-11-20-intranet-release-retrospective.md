## 失败、证据与处置

| 现象 | 原因与证据 | 本次修复 / 后续约束 |
| --- | --- | --- |
| 预检报不存在celery队列 | passive queue_declare对未声明队列返回404，不能直接视为发布失败 | 仅404按空队列；权限或连接错误必须失败。已有数字/字符串404测试 |
| 预检报worker繁忙或无响应 | active/reserved/scheduled未排空或inspect无响应；仅凭截图不能认定任务死锁 | 等待和采集现场，不清队列、不强杀；新旧路由切换前排空任务 |
| supervisord挂载报文件/目录不匹配 | 当前包目录中的旧挂载路径不再具备原文件；Docker缺失bind源可能被创建为目录 | 备份阶段固化配置文件，缺失时从原镜像恢复；确认类型后才能停止旧服务 |
| 解压后.latest-backup不存在 | 部署流程依赖包目录下的临时指针，新解压目录没有该状态 | resolve_backup按完整标记、版本与必要文件找备份；不能随意选一个目录，更不能重新覆盖原始备份 |
| 执行器密码挂载缺失或来源冲突 | 新包对原secrets布局和来源假设过强，历史恢复逻辑未完整继承 | prepare_assets保留原密码，候选冲突时验证凭据，不生成或重置平台登录密码 |
| API密码通过但执行器4401 | API登录密码和WebSocket token是两套鉴权，后端与执行器token不一致 | 保留既有后端token；为空时持久生成共享值，同步三个执行器，并验证后端实际加载值 |
| 回滚时Playwright MCP启动失败 | 复用旧容器仍依赖deploy_env中的入口脚本和模板；新包未完整携带 | 补齐原有入口与模板；保护有效文件、保留异常目录；发布和回滚前均检查 |
| 服务健康却自动回滚，KeyError: items | 05按View源码推断data.items；统一Renderer实际输出data.data.items | 有限层解析并校验状态、结构、ID和明确在线状态；用真实HTTP响应验证，不关闭验收 |
| ONES补丁报镜像不匹配 | 前次回滚后运行的是旧版本，补丁只允许精确的新版本 | 保留版本和源码SHA限制；成功发版后执行，不绕过保护 |
| ONES补丁连接超时 | 私有云无法连接目标IP端口，TCP连接阶段超时 | 网络策略开通后再验证TLS及接口；不能通过忽略证书或修改URL解决TCP不通 |

日志曾出现tee未生成文件的反馈，但现有材料不足以确认其具体原因，不把它写成已证实根因。后续统一保存带退出码的日志，使用set -o pipefail；失败日志须包含阶段、原始错误与回滚结果。

## 为什么旧坑又出现

已核对release-20261109-ai-coverage-r1/deploy_env：07-start-actuators.sh已有从备份、旧容器恢复密码的逻辑，docker-compose.update.yml已有Playwright入口和模板挂载。新版本采用运行态快照生成Compose，但没有把旧版本这些行为逐项迁移和验收。

因此问题在于发布工程的复用方式：修复散落在日期目录；复制新包时没有能力清单；测试存在但打包入口不强制运行；本地新安装验证也不能覆盖旧目录、旧挂载、缺失标记等升级状态。对最终HTTP接口缺少契约验证，又把验收脚本错误放大为全量回滚。这些是交付脚本与验证不足，不能归因于用户操作。

## 已落地的发布门禁

本版本新增verify_release.py，并由package.py在写入清单和ZIP之前强制调用：

1. 检查必要部署、回滚、凭据恢复、MCP和ONES补丁文件均为非空文件。
2. 检查全部Shell脚本语法。
3. 在精确Backend发布镜像内、禁用网络、只读挂载测试目录，运行明确列出的6个测试模块（目前15项）。覆盖缺队列、凭据恢复和冲突、token同步幂等、MCP异常目录、备份指针恢复、执行器响应与在线判定。
4. 任一失败停止打包。之后仍执行原有镜像版本、架构、原生组件验证记录、镜像分卷SHA和ZIP校验。

固定测试入口避免unittest discover导入具有实际启动行为的test_staging.py；宿主机也无需额外安装amqp。门禁只覆盖列出的场景，不等于完整升级/回滚演练，也不等于麒麟ARM64 64KB目标验收。

执行：python3 update_platform_version/release-20261119-89ffd9ef-r2/verify_release.py

## 下一阶段优化（尚未实施，后续发布前补齐）

- 将已验证发布引擎提取为单一共享实现；日期目录只记录版本、镜像和发布差异。迁移前保留旧版本用于比较，避免第三次重新实现。
- 在停服前验证所有实际bind源的存在性、文件/目录类型、可读权限及凭据有效性；不能只检查新Compose声明。
- 运行态配置和秘密固定在稳定的持久目录，发布包成为可替换的只读程序文件，避免覆盖解压破坏正在复用的容器依赖。
- 为打包结果增加发布包版本/哈希及适配的镜像ID，启动即打印；避免多个同名deploy_env.zip难以识别。
- 发布状态按预检、备份、启动、验收、提交、回滚记录；保留首个失败与退出码。区分部署健康失败、验收工具错误和可选外部集成不可达；工具错误时先采集健康证据，不能简单取消所有自动回滚。
- 构建升级与回滚演练夹具：旧版文件缺失、异常目录、候选密码冲突、标记丢失、token为空、半完成发布、回滚时基础设施复用。加入测试不等于完成演练；演练报告也须随版本保存。
- 外部依赖ONES等分别检测DNS/TCP/TLS/HTTP并给出精简错误；可选集成故障单独报告，核心发布完成后再处理。
