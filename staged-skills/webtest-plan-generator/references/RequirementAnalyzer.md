# RequirementAnalyzer：需求文档分析（入口B）

## 功能定位

解析用户提供的需求文档（PRD、功能规格说明等），提取功能点、业务规则、验收标准和测试维度，并与实际网站页面进行交叉验证。

## 前置条件

- 需求文档已提供（.docx / .pdf / .txt / .md 格式）
- **必须同时提供目标网站 URL**（用于后续页面验证）
- 若缺少 URL，应询问用户补充，否则无法保证用例质量

## 文档类型与处理能力

| 文档类型           | 可提取内容                             | 局限性                       |
| ------------------ | -------------------------------------- | ---------------------------- |
| PRD / 产品需求文档 | 功能模块、用户故事、业务流程、边界条件 | 可能缺少具体 UI 元素定位方式 |
| 功能规格说明书     | 详细功能点、输入输出定义、异常处理     | 技术细节可能过时             |
| 竞品分析文档       | 同类功能参考                           | 特定产品细节可能不适用       |
| 测试要点清单       | 已整理的功能点清单                     | 完整性依赖原始整理质量       |

## 分析流程

- 需求文档解析 → 功能点拆解 → 测试提取维度 → 补充页面验证

### 步骤 1：需求文档解析

- 读取文档内容，识别章节结构、表格、列表
- 提取功能模块名称、用户操作流程、输入输出规则
- 标记异常处理、边界条件说明

### 步骤 2：功能点拆解

将文档中的描述转化为结构化功能点清单，格式示例：

```json
{
  "module": "用户注册",
  "features": [
    {
      "name": "手机号注册",
      "precondition": "未登录状态",
      "steps": ["输入手机号", "获取验证码", "输入验证码", "设置密码", "提交"],
      "expected": "注册成功并自动登录",
      "exceptions": ["手机号已注册", "验证码错误", "密码格式不符"]
    }
  ]
}
```

### 步骤 3：测试维度提取

| 维度         | 对应测试点                   | 来源                  |
| :----------- | :--------------------------- | :-------------------- |
| 功能正确性   | 输入输出、计算逻辑、数据展示 | 功能规格说明          |
| 页面渲染     | 布局、样式、响应式           | UI/UX 文档或截图      |
| 交互流程     | 按钮点击、弹窗、表单提交     | 用户故事 / 流程图     |
| 权限与状态   | 登录态、角色差异、异常提示   | 需求说明中的前置条件  |
| 边界与异常   | 空输入、超长字符、格式错误   | 边界值分析 / 异常说明 |
| 性能与兼容性 | 加载速度、跨浏览器           | 非功能性需求（如有）  |

### 步骤 4：交叉验证（需网站 URL）

- 打开实际网站对应页面，对比文档描述与实际 UI、流程是否一致
- 标记差异点（如文档中存在的功能但页面上未找到）
- 若差异较大，询问用户以文档为准还是以页面为准

## 输出格式

分析完成后，生成 JSON 文件存入 `requirements_parsed.json`作为交付，结构示例：

```json
{
  "document_name": "xx平台PRD_v2.3.docx",
  "modules": ["用户注册", "商品搜索", "下单流程"],
  "features": [...],
  "discrepancies": [
    "文档提到'微信登录'，但页面无此按钮",
    "文档中注册步骤为4步，实际页面为3步"
  ],
  "cross_validation_done": true,
  "website_url": "https://example.com"
}
```

## 输出产物

执行完成后，输出目录结构如下，路径默认由主 skill 的 `交付物清单-输出目录` 决定

```
{OUTPUT_ROOT}/
├── analysis/				# 探索/分析结果目录（Step 1 产出）
│   └── requirements_parsed.json
```

## 注意事项

- **必须向用户确认**：是否同时提供网站链接？若无，建议补充
- 若文档内容与页面实际严重不符，生成用例前应提醒用户明确基准
- 对于未在文档中说明但页面上存在的明显功能（如分享按钮），可建议补充测试点
- 提取的功能点将作为 Step 2（测试方案生成）的输入，应保持原子性（每个功能点可独立测试）
