# 上证e投票平台测试报告生成

本 Skill 承担四阶段测试链路中的**报告生成阶段**，汇总同一链路的方案、用例、执行结果和证据，产出可离线复核的 HTML 报告与结构化统计。

## 前置门禁与输入

- 必须提供同一项目、同一 `workflow_id` 下通过门禁的方案、用例和执行产出引用。
- 执行结果需关联用例 ID，包含通过、失败、阻塞、未执行状态；截图、日志、证据、脱敏配置可用。
- 若用例全为空执行结果或缺失关键产物，先提示补齐，不生成虚假的“通过”报告。

## 执行流程

1. 按 `references/TestReport.md` 汇总方案、用例、执行产物，并按 D 需求、E 功能点分组；核对所有需求和范围收口条件。
2. 汇总截图、日志、SQL/Kafka/文件证据并按用例 ID 关联。失败、阻塞、需人工复核、重试轨迹与未执行项须保留。
3. 计算总通过率 `通过 ÷ (通过 + 失败)`，明确说明阻塞不计入该分母并单独展示；同时给出需求、功能点、执行方式、核心范围维度的统计。不得通过剔除失败项美化指标。
4. 依据 `references/回归清单.md` 对照本次实际回归范围，列出纳入/未纳入的子系统、用例数、结果、未覆盖原因与遗留风险。
5. 分别给出需求覆盖结论、失败清单、阻塞清单、需人工二次确认清单和发布建议；任何结论须与证据强度相称，不把部分抽查写成全面通过。
6. 输出单文件 `test_report.html` 和 `test_results.json`；HTML 离线可查看，截图/证据使用内嵌或包内相对路径。报告结构化正文满足平台 `workflow-report/v1` 契约。

## 报告必须披露

- 测试环境、执行人、执行时间、轮次。
- 总用例/通过/失败/阻塞/未执行、总通过率和核心功能通过率及公式。
- 每条需求的覆盖功能点数、用例数、结论与用例编号；白名单等范围收口要求须报告反向验证结论。
- 失败、阻塞原因、责任域、证据链接和遗留风险。
- 回归范围与清单差异，未覆盖设备/浏览器/系统链路，以及明确声明“本结论不隐含未覆盖项已验证通过”。
- JSON 必含 `coverage`、`pass_rate`、`failure_distribution`、`unclosed_issues`、三阶段上游产出引用。
