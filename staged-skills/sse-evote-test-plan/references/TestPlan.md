# TestPlan：测试方案生成（Step 2）

## 功能定位

将 Step1 的分析结论转化为**矩阵式系统测试方案**（复刻团队既有格式），明确测试里程碑、需求内容、测试策略、测试范围（覆盖大纲）、测试资源与测试风险。

> ⚠️ **本平台不使用"一行一个测试点"的平铺式方案表**。既有格式是 A 列固定 6 大模块 + B 列子项 + C:F 合并承载正文文本块的矩阵表。生成时必须复刻，否则无法汇入既有方案库。

## 输入要求

- Step1 产出：`analysis/requirements_parsed.json`（或 `page_structure.json`）
- 可选：用户补充的里程碑日期、执行人与工时
- **既有 `test_plan.xlsx`（有则必读）**：作为格式基线，并复用其"测试覆盖大纲"的编号体例

## 模板文件

`templates/测试方案_template.xlsx`（Sheet：`测试方案`） —— 表头、合并单元格、配色与列宽均已就位，**在模板上填充，不要重建表结构**。

## 表结构与填写规范

```
A1（A1:F1 合并）  {产品}_{迭代需求}_系统测试方案
```

### 模块 1：测试里程碑

| 位置 | 字段 | 说明 |
| --- | --- | --- |
| A2:A3 合并 | 测试里程碑 | 分组标签 |
| B2 / C2 / D2 / E2 / F2 | 测试设计完成日期 / 评审日期 / 提测日期 / 回归完成日期 / 系统上线日期 | 字段名 |
| B3:F3 | 对应日期 | 单元格格式 `yyyy/m/d`；未确定填"待定" |

### 模块 2：需求内容

| 位置 | 内容 |
| --- | --- |
| A4 | `需求内容` |
| B4 | `需求内容/项目目标` |
| C4:F4 | 用 `1、2、3、` 编号列出本次需求项，**每条一句话说清"改了什么、为谁解决什么问题"** |

示例：

```
1、 投票新版网站相关优化：日期选择栏更换为中文组件、增加投资者调研问卷二维码、小程序嵌入H5兼容优化；
2、 采编系统增加时间戳的字段：针对"会议ID+时间戳"新增唯一性约束；
3、 股权处理自动化功能三阶段优化：上市公司点击提交股权处理申请时，新增自动生成说明文稿和提示框内容功能，提升用户体验；
```

### 模块 3：测试策略（A5:A8 合并 = `测试策略`）

固定 4 类，B 列写子项名，C:F 写内容：

| B 列 | 内容要求 |
| --- | --- |
| 功能测试策略 | 写明测试角度，默认沿用：`数据驱动测试，主要角度：1，功能错误或者遗漏；2，业务流程测试；3，数据的正确性；4，界面错误；5，角色权限控制；`（按本次需求增删） |
| 兼容性测试策略 | 引用 `references/投票业务规则库.md` 第 7 节矩阵；未覆盖项必须在此显式声明 |
| 关联性测试策略 | 写明跨系统联动点，如 `前后台数据联动` |
| 回归测试策略 | 写明回归依据，默认 `改动涉及的模块与功能回归`；具体范围见 `references/回归清单.md`，在"测试范围"中展开 |

### 模块 4：测试范围（A9:A18 合并 = `测试范围`，B9:B18 合并 = `测试覆盖大纲`）

**这是方案的核心**。每条迭代需求各占若干行，正文写在 C 列（C:F 合并），采用**三段式编号**：

```
{需求名}                      ← 一级：需求名，可用"一、二、三"或直接写需求名
一、 {功能模块/验证主题}        ← 二级
1、  {具体测试点，写明操作 + 判定}   ← 三级
  1.1、 {更细的分支}            ← 四级（缩进 2 个空格）
```

**写作要求**：

| 要求 | 说明 |
| --- | --- |
| 一个测试点一句话 | 单行内写清"在哪、做什么、验证什么"，不写空话 |
| 分层不超 4 级 | 与用例的 E 列（四级模块）对齐，便于 Step3 直接映射 |
| 覆盖三场景 | 每个功能点包含正向 + 反向/边界；白名单类需求必须含"不开放类型确实不开放" |
| 数据类写清判定对象 | 涉及入库/消息/文件的，写明表名、字段、文件名规则 |
| 组合场景用矩阵描述 | 开关 × 状态 × 操作组合较多时，在方案中列出组合维度，不必逐条穷举 |
| 回归段必含 | 末尾单列"回归测试："段，按子系统分组（引用 `references/回归清单.md`，按本次改动裁剪） |

**缩进约定**：层级靠文本内缩进表达（每级 2 个半角空格），**不使用单元格缩进设置** —— 沿用既有习惯。

### 模块 5：测试资源（A19:A21 合并 = `测试资源`，B19:B21 合并 = `测试资源/范围/工时`）

| 行 | C 列（C19:C21 合并，执行人） | D:E 列（合并，工作项） | F 列（工时） |
| --- | --- | --- | --- |
| 19 | 执行人姓名（多人用顿号） | 需求分析、测试方案、用例编写、评审及修改 | 人日 |
| 20 | 同上 | 测试环境测试执行、回归测试 | 人日 |
| 21 | 同上 | 测试报告编写及评审 | 人日 |

> 参考量级（既有产出）：6 + 20 + 1 = 27 人日 / 3 人。实际按本次需求规模调整，**须与执行人确认**。

### 模块 6：测试风险（A22:A25 合并 = `测试风险（包括预估风险和预防措施）`）

固定 4 类，B 列写类型，C:F 写内容：

| B 列 | 内容 |
| --- | --- |
| 资源风险 | 如"经项目组确认兼容性覆盖如方案所述，未能覆盖浏览器/机型可能带来结果异常的风险" |
| 环境风险 | 无 / 具体说明 |
| 时间风险 | 无 / 具体说明 |
| 技术风险 | 无 / 具体说明 |

> ⚠️ **"无"不等于没风险**。凡有未覆盖项（设备、环境、依赖外部配合），必须落到对应风险条目，**禁止用"无"掩盖已知缺口**。

## 生成步骤

1. **收集输入**：Step1 的功能点清单、业务规则、白名单约束、待确认清单。
2. **确认里程碑**：向用户确认 5 个日期（缺失则填"待定"）。
3. **写需求内容**：按需求项编号概述。
4. **写测试策略**：4 类，兼容性矩阵引用规则库。
5. **写测试范围**：按需求逐条展开三段式大纲；末尾补"回归测试"段（引用回归清单，按改动裁剪）。
6. **写测试资源**：执行人 + 3 项工作项 + 人日。
7. **写测试风险**：4 类；未覆盖项必须落实。
8. **交叉核对**：与 Step1 功能点清单对比，确认无遗漏模块；与规则库对比，确认白名单反向验证、数据链路验证均已包含。
9. **保存**：`test_plan.xlsx`。

## 注意事项

- 方案编号一旦确定不应随意变更（影响用例追溯）。
- 若发现 Step1 遗漏，返回补充后再生成方案。
- **同一需求项不要重复出现在多个内容块**；跨子系统的验证点按子系统分列。
- 复杂功能（如股权处理）可用多个 C 列行展开，不必挤在一条。
- 有历史方案时参考复用，但需重新评估覆盖率（尤其白名单、开关组合等新增约束）。
