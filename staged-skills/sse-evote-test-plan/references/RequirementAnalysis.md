# RequirementAnalysis：需求文档与资产分析（Step1-A）

## 功能定位

解析用户提供的需求文档（《需求方案》+ 原型图 + 字段/样例附件），提取功能点、业务规则、验收标准与测试维度，并与既有测试资产（历史方案/用例）和实际系统交叉验证，产出结构化「测试基准」，作为 Step2 测试方案与 Step3 测试用例的唯一输入。

## 前置条件

- 已获取需求文档（`.docx` / `.pdf` / `.md`）。**若文档含原型图截图**，需读取截图内容 —— 交互细节、字段枚举、错误文案通常只存在于原型图中。
- 已获取（有则必读）既有 `test_plan.xlsx` / `test_cases.xlsx` —— 用于复用模块层级（D/E 列）、编号区间与判定口径。
- 可选：目标系统 URL（用于交叉验证）。

> 与通用 Web 测试不同：本平台**不强制要求 URL**。因为大量需求（采编、基础服务、统计系统）本身就没有前台页面，验证对象是数据与流程。缺少 URL 时不要阻塞流程，改为标注"UI 层待页面探索补充"。

## 分析流程

```
需求文档解析 → 原型图解析 → 功能点拆解 → 业务规则抽取 → 与既有资产对齐 → 待确认清单
```

### 步骤 1：需求文档解析

- 读取章节结构（背景介绍 / 需求描述 / 原型图及附件）。
- 提取：**需求来源与依据、需求背景、需求优先级、需求范围（涉及哪些子系统）**。
- 逐条提取需求项，记录其**优先级**与**期望完成时间**。

### 步骤 2：原型图解析（关键且易被跳过）

对每一张原型图，逐个区域提取：

| 提取对象 | 说明 |
| --- | --- |
| 页面/组件结构 | 元素位置、层级、弹窗组成（如"文件预览在左、提示文字在右"） |
| 按钮与状态 | 按钮文案、置灰/高亮条件 |
| 字段与枚举 | 下拉项、单选项、默认值、必填/非必填 |
| 文案 | 提示文字、错误提示、温馨提示、勾选框文案（**逐字记录**） |
| 跳转 | 点击后的目标页面/地址 |

> 原型图是**文案与交互的唯一权威**。文档正文没写的错误提示、枚举取值，都必须回到原型图确认。

### 步骤 3：功能点拆解

将需求描述转化为结构化功能点。**粒度以"四级模块（E 列）"为准** —— 即"一个可独立验证的功能点"。

```json
{
  "iteration": "202601",
  "requirement": "股权处理自动化功能三阶段优化",
  "module_path": {
    "用例库": "上证e投票平台",
    "一级模块": "投票业务子系统",
    "二级模块": "迭代版本用例",
    "三级模块": "202601_股权处理自动化功能三阶段优化"
  },
  "features": [
    {
      "四级模块": "股权处理提交非空流程-提示页面验证",
      "端": "业务系统前台",

```

### 步骤 4：业务规则抽取（本平台的价值所在）

按 `references/投票业务规则库.md` 的框架逐项抽取，**尤其不能漏**：

- **白名单/范围约束**（哪些会议类型开放功能）→ 必然产生"反向验证"用例；
- **唯一性与去重规则**（如 `会议ID + 时间戳`）；
- **状态与流程**（流程类型、流程状态、状态流转条件）；
- **开关配置**（有哪些开关、开关与场景的组合）；
- **字段级约束**（公告类型与流水号/id 的取值规则、必填与可变字段）；
- **生成物规则**（文件名拼接、模板格式、动态字段）；
- **交互约束**（按钮置灰条件、跳转地址、返回按钮显隐、字体）。

### 步骤 5：与既有资产对齐

- 读取既有 `test_cases.xlsx`，复用 A/B/C/D 列的值与 E 列的命名风格；
- 复用既有 E 值下的编号区间，**新增用例追加在末尾**，不重排历史编号；
- 复用既有的判定口径写法（如表字段校验、文案校验的表述方式）。

### 步骤 6：产出待确认清单

凡素材未明确的（环境地址、账号、数据获取方式、完整错误文案、状态机、任务触发方式），逐条列为 `open_questions`，**在生成用例前先向用户确认**；用户不便确认时，按"标注待确认 + 用例中留占位符"处理，不要凭空补造业务规则。

## 注意事项

- **不要跳过原型图**：正文常写"业务规则不涉及"，真实规则在截图里。
- **白名单类需求必须产出反向用例**，这是本平台最高频的漏测点。
- **不要凭空生成无来源的业务规则**：无来源的一律进 `open_questions`。
- **需求描述与既有用例冲突时**以需求为准，并在 `open_questions` 中记录冲突点，请用户裁决。
- 功能点应保持**原子性**（每个可独立测试），避免一个四级模块塞进多个不相关的功能。
