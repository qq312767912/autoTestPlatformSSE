# 全平台质量飞轮接入需求

## 1. 目标

将质量飞轮建设为全平台公共能力，而不是某个独立控制台的附属功能。所有业务模块使用同一套产出协议写入可追溯数据，后续统一支持金标建设、自动评测、轨迹归因和优化验证。

首批接入八个业务阶段：

1. 用例审查 `case_review`
2. 代码审查 `code_review`
3. 测试方案生成 `test_plan_generation`
4. 用例生成 `testcase_generation`
5. 代码需求提取 `code_requirement_extraction`
6. 风险识别 `risk_identification`
7. 测试执行 `test_execution`
8. 问题跟踪 `issue_tracking`

## 1.1 两类飞轮

- **链路型自进化**：`risk_identification → test_plan_generation → testcase_generation → test_execution → issue_tracking`。使用同一 `workflow_id` 串联上下游，通过 `parent_output_ids` 保留分支与汇聚关系；同时评测阶段质量和端到端业务结果。
- **单次型测评**：`case_review`、`code_review`、`knowledge_query`。每次能力调用独立形成输入、输出、证据、反馈与评分，可按同类样本聚合为优化候选，不强制依赖下游阶段。

## 2. 范围

### 本阶段包含

- 定义与业务模型解耦、可版本化的统一产出协议。
- 建设公共发布服务，统一完成幂等、脱敏、持久化和失败降级。
- 为八个业务阶段分别提供薄适配器，将现有产出映射到统一协议。
- 建立输入、产出、证据、人工反馈、后续结果之间的关联标识。
- 保持业务主流程可用：飞轮记录失败不得导致业务任务失败。
- 为每个适配器提供契约测试和至少一个真实流程集成测试。
- 复用现有 `RetrievalTrace`、`GenerationOutput`、`FeedbackEvent` 作为第一阶段存储，不要求业务模块直接依赖这些模型。

### 本阶段不包含

- 继续扩展独立的飞轮控制台。
- 自动修改并发布 Prompt、工具或模型。
- 在没有人工确认的情况下自动把业务产出升级为金标。
- 为了接入飞轮而重写八个业务模块的核心流程。

## 3. 统一产出协议要求

每条产出必须包含以下稳定字段：

- `schema_version`：协议版本。
- `event_id`：全局事件标识。
- `idempotency_key`：同一业务产出的稳定幂等键。
- `project_id`：所属项目。
- `stage`：八个标准业务阶段之一。
- `producer`：模块、能力、版本和运行环境。
- `source`：业务对象类型、业务对象 ID、父对象和入口。
- `execution`：本次运行 ID、状态、开始/结束时间和耗时。
- `input`：任务目标、输入摘要及输入内容哈希；默认不复制敏感原文。
- `output`：结构化产出摘要、内容哈希、产物引用和数量统计。
- `findings`：问题、风险、建议、用例或执行结果等标准化条目。
- `evidence`：文件、代码行、需求段落、用例、日志或截图等证据引用。
- `lineage`：上游产出、下游产出、Prompt、模型、工具和知识版本引用。
- `evaluation_mode`：`single` 或 `workflow`。
- `workflow_id`：链路型自进化的稳定流程标识；单次型允许为空。
- `parent_output_ids`：直接上游产出，可表达一对多、多对一和重跑。
- `metrics`：Token、成本、覆盖率、通过率和业务自定义指标。
- `feedback_targets`：允许后续反馈精确关联的对象键。
- `privacy`：脱敏状态、保留级别和禁止进入模型训练的标记。

协议必须允许 `extensions` 承载模块特有数据，但公共消费方不得依赖未声明的扩展字段。

## 4. 用户故事与验收标准

### R1：统一发布

作为平台开发者，我希望各模块只调用一个公共发布接口，以便飞轮数据的幂等、脱敏和存储规则保持一致。

- 当任一业务模块完成、失败或产生部分结果时，系统应接收一个符合当前协议版本的产出信封。
- 当相同 `idempotency_key` 被重复提交时，系统应返回同一条记录，不重复写入。
- 当飞轮持久化异常时，系统应记录可检索错误，但不得改变原业务任务的最终状态。
- 当协议校验失败时，系统应指出字段路径和失败原因，并禁止写入不完整数据。

### R2：全链路关联

作为测试负责人，我希望从任一产出追溯其输入、证据、人工反馈和后续结果，以便定位失败节点并沉淀 Badcase。

- 当产出来自另一个平台产出时，系统应通过 `lineage.parent_output_ids` 建立关系。
- 当风险分析进入测试方案、用例、执行和问题跟踪时，系统应保持同一 `workflow_id`，不得仅按文本相似度推断上下游关系。
- 当链路中某阶段被重跑时，系统应保留旧产出并用 `supersedes_output_id` 指向被替代版本。
- 当用户采纳、驳回、编辑、确认缺陷、标记误报或漏报时，反馈应能关联到整条产出或单个 finding。
- 当测试执行验证了上游风险、需求或用例时，执行结果应能关联到对应上游产出。

### R3：八模块接入

作为平台使用者，我希望八个业务阶段都能自动进入飞轮，以便质量改进覆盖完整测试流程。

- 当用例审查完成时，系统应记录审查结论、问题项、证据和人工处置目标。
- 当代码审查完成时，系统应记录完整审查覆盖、缺陷分层、反证结论和代码证据。
- 当测试方案生成完成时，系统应记录范围、策略、场景、风险和引用需求。
- 当用例生成完成时，系统应记录生成用例、覆盖目标、来源需求和后续执行关联键。
- 当代码需求提取完成时，系统应记录提取需求、代码依据、置信度和后续确认目标。
- 当风险识别完成时，系统应记录风险等级、影响范围、证据和建议验证项。
- 当测试执行结束时，系统应记录用例结果、失败证据、耗时和上游用例引用。
- 当问题状态变化时，系统应记录问题创建、确认、修复、复测和关闭结果，并关联最初发现它的产出。

### R4：可评测与金标候选

作为测试负责人，我希望真实业务产出能被筛选为评测样本和金标候选，以便持续建设专属评估资产。

- 当产出收到缺陷确认、误报、漏报、人工编辑或复测结果时，系统应更新其金标候选资格。
- 当产出证据不足、来源不可追溯或包含禁止使用数据时，系统不得自动进入金标候选集。
- 当金标候选被采用时，系统应保存标注人、标注时间、协议版本和来源快照。

### R5：兼容与演进

作为平台维护者，我希望协议可演进且不锁死业务模块，以便后续增加新阶段和新的评测方式。

- 当新增可选字段时，旧适配器和旧消费者应继续工作。
- 当发生不兼容变更时，系统应提升主版本并提供显式转换器。
- 当新增业务阶段时，应通过注册适配器接入，而不是修改公共发布服务的条件分支。

## 5. 非功能要求

- 公共发布调用在正常数据库条件下，P95 额外耗时目标小于 50ms；耗时较大的加工使用异步任务。
- 原始代码 Diff、密钥、Token、Cookie、账号和完整敏感文档默认不得写入飞轮表。
- 所有记录按项目权限隔离；读取、导出和金标审批沿用项目成员权限与审计日志。
- 协议序列化结果必须稳定，可用于哈希、重放和离线评测。
- 八个适配器必须支持开关和灰度接入，可独立关闭而不影响业务主流程。

## 6. 完成定义

- 统一协议、校验器、发布服务和适配器注册表可用。
- 八个适配器均通过契约测试。
- 八个真实业务流程各至少产生一条可追溯产出。
- 重复回调不产生重复记录，敏感字段不会落库。
- 任意飞轮写入故障均不阻断原业务流程。
- 现有代码审查、测试执行和用例生成接入迁移到统一接口，行为保持兼容。
