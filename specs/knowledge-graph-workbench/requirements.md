# 知识图谱工作台需求

## 目标

建设统一的知识图谱查看与检索入口。第一期展示 CRG 产生的代码仓库图谱，后续可接入知识库文档、需求、测试用例和缺陷，形成可被 LLM 检索的知识沉淀与数据飞轮。

## 验收需求

### R1. 统一图谱数据源

- 当用户进入图谱工作台时，系统应只列出其有权限访问的项目图谱源。
- 图谱源应使用统一结构表示类型、名称、项目、版本、状态、统计和来源追踪信息。
- 第一期应支持 `code_repository`；协议应允许未来增加 `knowledge_document`、`requirement`、`test_case` 等类型。

### R2. 代码仓库图谱展示

- 当用户选择已建图的代码仓库时，系统应展示文件、类、函数、测试等节点以及调用、导入、继承、引用等边。
- 当图谱规模超过浏览器预算时，系统应返回有上限的概览或节点邻域，不应一次传输完整 SQLite 数据。
- 当用户搜索或点击节点时，系统应返回该节点的属性、来源路径、行号、调用方、被调用方和关联测试。

### R3. 检索与筛选

- 用户应能按节点名、文件路径、节点类型和边类型筛选。
- 当用户更换图谱源、搜索词或筛选条件时，页面应显示加载状态、空状态或可操作的错误状态。

### R4. 权限与数据边界

- 前端不应直接访问 CRG，不应获得 CRG Token、SQLite 路径或容器绝对路径。
- 当用户请求无权项目的图谱时，Backend 应拒绝请求。
- 图谱返回数据应将仓库绝对路径归一化为仓库相对路径。

### R5. 可追踪与 LLM 消费

- 每个节点和关系应保留 `source_type`、`source_id`、`snapshot_id`、置信度和来源位置。
- 统一协议应允许后续将选定节点邻域转换为带引用的 LLM 上下文，但本期不新增自动写入 LLM 的隐式流程。

## 非目标

- 本期不把知识库文档真正转换为图谱，只交付适配协议和扩展点。
- 不允许前端输入任意本地目录。
- 不向普通用户开放原始图数据库下载或任意 SQL/图查询。
