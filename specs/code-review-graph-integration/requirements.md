# 代码变更分析图谱增强需求

## 1. 背景与目标

WHartTest 现有代码变更分析已支持 GitLab Merge Request/两个 Commit、共同祖先 Diff、规则检查、Semgrep、OpenCodeReview、平台 LLM 分析、反证核验、测试需求点和报告导出。本次改造不替换这条链路，而是引入 `code-review-graph` 作为“代码结构、依赖关系和影响面证据引擎”。

核心目标：

1. 在不减少变更文件覆盖的前提下，为每个变更补充跨文件依赖、受影响函数、执行流和测试缺口。
2. 用图谱定位的上下文替代现有粗粒度的“声明抽取 + grep”补充上下文，降低 LLM 无效输入与跨文件误判。
3. 保留平台现有的结论语义：确定缺陷、待确认风险、改进建议；图谱风险分不得直接等同于缺陷。
4. 在内网、麒麟 ARM64 64KB 页环境下可离线部署、可观测、可降级和可回滚。

## 2. 用户故事

### R1. 图谱生命周期

作为测试人员，我希望平台在分析仓库时自动准备并更新代码图谱，无需手工执行 CRG 命令。

- 当仓库首次执行分析时，系统应构建该目标 Commit 的图谱并记录状态、版本、耗时与解析覆盖。
- 当同一仓库分析新 Commit 时，系统应优先执行增量更新；当图谱不兼容、损坏或基线不可达时，系统应重建图谱。
- 当部分文件解析失败时，系统应标记图谱为 `partial`，保留失败文件清单，并继续原有分析链路。
- 当仓库配置被删除或管理员手动清理时，系统应删除其工作副本与图谱数据，不影响历史报告。

### R2. 全量变更覆盖

作为开发和测试人员，我希望所有可分析变更都被审查，不因图谱排序或 token 预算被静默丢弃。

- 当 Diff 包含多个文件或大文件时，系统应继续对全部可分析 Diff 分批处理。
- 当 CRG 返回结果因上限被截断时，系统应记录总数、已展示数与截断标记，不得将“未返回”解释为“无影响”。
- 当图谱上下文超出 LLM 预算时，系统应优先保留变更 Diff，再按影响分数和证据完整度裁剪补充上下文。

### R3. 影响面证据

作为开发人员，我希望每条风险能展示“为什么受影响”，而不只是给出一个结论。

- 当变更命中图谱节点时，系统应返回变更函数/类、直接与间接依赖、受影响文件、关联测试和执行流。
- 当影响关系是推断而非解析所得时，系统应展示其边类型、置信度和路径，并作为待确认证据处理。
- 当图谱无法将某变更文件映射到节点时，系统应显式显示“图谱未覆盖”，不得宣称影响面为空。

### R4. 结论分类与反证

作为开发人员，我希望平台区分已证实问题、需人工确认的风险与非正确性改进。

- 当 CRG 给出高风险分或大影响半径时，系统应将其作为审查优先级和反证线索，不得直接生成“确定缺陷”。
- 当一条候选结论经目标 Commit 源码、调用路径和相关定义验证后，系统应将其归类为 `confirmed`、`needs_confirmation`、`advisory` 或排除。
- 当结论被排除时，系统应保留排除数量和反证原因供审计，但不向开发者交付为有效问题。

### R5. 测试影响与覆盖缺口

作为测试人员，我希望报告能从代码调用关系推导需回归的模块、执行流和未覆盖热点。

- 当变更影响已索引的测试节点时，系统应把关联测试纳入回归建议。
- 当高影响函数没有测试关联时，系统应生成可追溯的测试覆盖缺口，但不自动宣称业务功能未测试。
- 当生成测试需求点时，系统应保留来源变更、影响路径、风险结论和可判定预期。

### R6. 任务、降级与审计

作为平台管理员，我希望图谱增强不会让现有审查因单个组件故障而整体不可用。

- 当 CRG 服务超时、异常或图谱构建失败时，系统应记录原因，并降级至当前的规则/Semgrep/LLM/OCR 链路。
- 当用户取消任务时，系统应终止本次图谱构建或查询的子进程/请求，不留孤儿进程。
- 当任务完成时，系统应在执行日志中保留 CRG 版本、图谱 Commit、构建状态、节点/边数、查询截断、耗时与降级信息。

### R7. 安全和数据边界

作为平台管理员，我希望图谱引擎只能读取被授权任务的仓库，不暴露任意文件或密钥。

- 当后端请求 CRG 时，系统应使用平台分配的仓库标识和服务端解析路径，不接受前端传入的任意绝对路径。
- 当仓库内存在 `.code-review-graph` 或定制配置时，系统应将其视为不可信仓库数据，不允许其扩大服务可访问边界或执行任意命令。
- 当导出图谱数据时，系统应提示其可能包含绝对路径和代码结构元数据，且默认不对普通用户开放原始导出。

### R8. 界面与报告

作为分析报告使用者，我希望看到可解释的影响概览，而不是复制 CRG 的原始 JSON。

- 当图谱分析成功时，系统应在报告中展示图谱状态、变更函数、受影响模块、关键执行流、测试缺口和上下文节省估算。
- 当用户查看某条风险时，系统应允许展开对应的依赖路径与关联测试，同时保留 Diff 证据。
- 当 HTML/Markdown 报告导出时，系统应包含与界面一致的图谱概要和降级说明。

## 3. 约束

- 主集成分支仍为 `dev`，实施时从 `dev` 创建 `feature/*` 分支。
- 内网目标为麒麟 ARM64 64KB 页环境；必须交付可离线安装的 Python wheel/镜像并在 Alpine/musl ARM64 环境验证。
- 现有 Django 后端依赖 `mcp>=1,<2`；CRG 2.3.9 依赖 `mcp>=1,<3` 和 `fastmcp>=3.2.4,<4`。方案不得未经隔离直接升级主后端 MCP 依赖。
- CRG 当前为 MIT 许可；交付物需保留许可声明并将版本锁定到验证过的版本/提交。
- 快速模式保持零 LLM 调用；是否启用图谱快速查询由后续设计确定，但不得显著拉长其时延。

## 4. 非目标

- 不用 CRG 替换 Semgrep、OpenCodeReview、专用 LLM 或现有反证流程。
- 不在本期开放通用 MCP 客户端、任意图查询或对外公网服务。
- 不在本期将 CRG 的语义向量模型作为必选依赖；先使用 Tree-sitter + SQLite/FTS + 图遍历。
- 不因图谱优先级排序而减少全量 Diff 审查覆盖。
- 不把图谱可视化工具的 D3 页面直接嵌入生产管理界面；页面需要按 WHartTest 的权限、语义和交互重新设计。

## 5. 建议的验收基线

1. 在一个包含 Python/Vue 且至少 1,000 个源码文件的基准仓库上，首次构建、两文件增量更新、图谱损坏重建均可验证。
2. 对人工标注的跨文件变更集，受影响文件召回率不低于改造前，且所有变更文件审查覆盖率保持 100%。
3. 与现有标准模式对照，LLM 的非 Diff 源码上下文输入中位数下降至少 30%，跨文件可解释结论数增加，且确定缺陷误报数不上升。
4. CRG 完全不可用时，原有快速/标准/深度模式仍能结束为完成或降级完成，并在报告中明示降级原因。
5. 取消、重试、仓库删除、历史报告回看和两个 Commit 共同祖先比较的现有行为不回归。

## 6. 已确认的 PoC 边界

1. CRG 以独立容器离线安装，不进入 Backend 主镜像。
2. PoC 复用审查任务的浅仓库，并使用独立图谱目录；仓库对 CRG 只读，图谱目录对 CRG 可写。
3. 影响文件、调用方、已有测试和受影响流程通过受限适配层写入现有 `CodeReviewMCP.collect_context()` 返回值。
4. 全部可分析 Diff 仍必须被审查；CRG 只增加上下文，不作为文件筛选器。
5. 用平台真实 Java、Python、Vue 仓库做改造前后对照，记录 Token、审查耗时、确定缺陷采纳率、漏报率、误报率、首次图谱构建耗时和增量更新耗时。
6. PoC 达标后，再决定是否实施跨任务长期图谱缓存和前端影响链展示。

## 7. 待设计阶段固化的细节

1. CRG 内部 API 的请求/响应结构、超时、取消、并发和降级契约。
2. PoC 的图谱是“任务级临时持久”还是“仓库级短期复用”；两者都不等同于正式长期缓存。
3. Java、Python、Vue 基准仓库的人工标注变更集、样本数和 PoC 通过阈值。
