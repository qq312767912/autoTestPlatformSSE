# 一本化文档版本对比与 Diff 提取

## 用户流程

需求管理 → 版本对比与提取→ 上传旧版和新版 DOCX → 查看红删绿增差异 → 勾选变更块 → 填写迭代名称并人工确认 → 下载 ZIP → 解压后把迭代需求 DOCX 上传为普通文档。

全程不调用 AI；不根据修订日期猜测迭代归属。上传入口统一为普通需求上传，不再要求选择管理方式。后端 management_mode 字段仅保留用于兼容历史数据，不再决定界面或流程。不新增10MB硬限制，继续遵循已有上传基础设施限制。

## 解析与对比

使用现有 python-docx 1.1.2 及其 lxml 底层，直接解析 DOCX。当前阶段未引入 docx-trackdiff 或 .NET 引擎，避免把其生成红线文档的流程强套到结构化预览中。

两份文件均按接受修订后的有效视图解析，手工删除线和双删除线视为删除；处理直接格式、字符样式和段落样式继承。支持正文内容控件、文本修订、表格删除行。明确保留数字、单位和链接目标差异；图片内容散列参与匹配，表格边界与合并结构参与匹配。

按正文段落和整表生成差异，SequenceMatcher 对齐相同块；修改显示为旧块删除和新块新增，保留两块上下文。默认左旧右新展示，也可切换统一视图；修改段落中的具体文字加深高亮。行号为有效内容块序号，不是 Word 页码。章节路径用于定位，不依赖分页渲染。

页眉页脚、批注、自动编号及纯样式变化不参与业务对比。图片按需加载缩略图；表格使用可读的单元格展示，选择粒度仍为整块。

## 人工确认与导出

按变更块勾选，全选/清空；修改选择、文件或迭代名称后重置确认。没有差异时不能提取。会话保存在后端，浏览器可恢复本项目最近一次对比。

确认请求携带迭代名称与变更块ID。服务端核对选择及新版文件散列，然后生成新 DOCX 包，只复制所选新版有效块，附章节路径，保留表格、普通内嵌图片和超链接。不会把完整源文件包装成一个裁剪显示的文件，避免隐藏正文混入输出。

下载 ZIP：
- 迭代需求.docx：新增/修改后的有效小节及取消/修改需求，可重新上传为普通文档。
- 变更说明.md：所选新增、修改前后和删除记录，附源文件SHA256。

只有删除项时仍生成取消/修改需求，保留原规则和来源；不根据局部删字擅自认定整项功能取消。普通Word域（目录、交叉引用等）保留已保存的显示结果，导出时去除域指令，Choice/Fallback只保留一份。脚注、图表、嵌入对象等暂不能完整复制的内容，在预览中标明来源位置，选择后导出会提示具体变更位置。书签等非正文标记不再误报遗漏。

## API 与数据

新增 RequirementComparison：项目、创建人、两份原文件、原名、差异JSON、已确认变更块、迭代名称和确认时间。源文件配对一旦建立不提供编辑接口。

- POST /api/requirements/comparisons/：multipart，project / old_file / new_file。
- GET /api/requirements/comparisons/{id}/：恢复对比。解析版本更新时重建差异并清除旧确认，要求重新核对。
- GET /api/requirements/comparisons/{id}/image/?side=old|new&rid=...：鉴权后读取属于本次文档的图片缩略图，不接受任意文件路径。
- POST /api/requirements/comparisons/{id}/confirm-extract/：JSON，title / hunk_ids，返回ZIP。

要求登录及项目成员身份，会话仅创建人可读和确认，超级管理员可访问；成员资格撤销后不能再访问。原始需求文档和文件不被替换。

## 部署与当前边界

执行 requirements 的 0014、0015 数据库迁移，发布前后端代码。测试只在隔离SQLite及临时媒体目录执行，未修改业务数据库。

当前请求同步执行；加载提示不是后台任务进度。尚未实现后台队列、并发配额或大范围修改下的进一步优化，不承诺任意规模文档的耗时。真实千页复杂文档及麒麟环境仍需现场验证。
