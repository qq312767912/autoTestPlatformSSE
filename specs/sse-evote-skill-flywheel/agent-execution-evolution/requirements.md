# 质量飞轮—Agent 执行—Skill 自进化联动需求

> 状态：待确认  
> 上位需求：[`../requirements.md`](../requirements.md)  
> 本文只收录本次专项开发的最小需求范围。

## 1. 目标

在不重建 Agent 的前提下，将质量飞轮与现有方案分析、用例生成、测试执行和报告产出联动，使每次受控运行能够锁定版本、观察执行过程、登记正式产出、收集最小人工反馈，并以受控方式派生和评测 Skill 候选版本。

目标链路：

```text
飞轮发起流程
→ 原业务页面执行 Agent
→ 正式产出与证据链
→ 人工确认/补充文件
→ 差异与归因
→ Skill 候选
→ 对照评测
→ 审批、激活与回滚
```

## 2. 核心原则

1. 质量飞轮是控制面、观测面和反馈面，原 Agent Runtime 是唯一执行面。
2. 受控模式与直接业务入口共用同一套 Agent 和统一产出协议。
3. 不强制所有 Skill 使用相同业务文件模板，只统一机器可读产出信封。
4. 不采集、展示或依赖模型隐藏思维链；使用显式结构化决策记录。
5. 人工确认尽量简化，只填写结论、修改类型、修改内容和备注。
6. 上传反馈、确认归因、派生候选、评测、发布相互独立。
7. 所有流程、产出、反馈、文件和候选按项目隔离并可审计。

## 3. 用户故事与验收需求

### R1. 飞轮发起与版本锁

当测试负责人从飞轮发起流程时，系统应为四阶段锁定具体 SkillVersion 和包哈希；运行中不得因 Skill Hub 激活新版本而漂移。

### R2. 阶段执行联动

当用户点击方案阶段执行入口时，系统应校验前置门禁、创建执行尝试并自动跳转方案分析；用户不得手工复制 `workflow_id`、`module_key` 或 SkillVersion。

### R3. 可信执行上下文

业务页面应通过服务端执行上下文解析流程、阶段、锁定 Skill 和父产出；篡改 URL、项目切换、上下文过期或版本不一致时必须拒绝执行。

### R4. 运行尝试与正式产出

每次运行必须先创建 `StageExecutionAttempt`。即使 Agent 中途失败，也应保留运行状态和已有轨迹；只有正式提交后才创建或绑定 `GenerationOutput`。

### R5. Agent 中间过程

系统应记录输入准备、检索、工具调用、文件生成、校验、正式发布和失败等可观察事件，并保存工具名、状态、耗时、哈希和受限错误摘要。

系统不得把隐藏思维链、账号凭据、完整敏感参数或大段工具返回写入观测数据。

### R6. 标准产出信封

L2/L3 Skill 应提交 `stage_result.json`，至少声明阶段、状态、主产物、稳定业务项 ID、需求关联和证据引用。业务 Excel、PDF 或 HTML 格式可继续由 Skill 自定义。

### R7. 知识原句追溯

证据引用应包含文档、版本、Chunk、原句、offset 和哈希。平台必须验证原句真实存在；只有验证通过的引用才能标记为可信证据。

### R8. 执行证据图谱

平台应连接需求、知识原句、结构化决策、工具调用、业务项、正式产物、人工修改、失败归因、Skill 补丁和评测结果。图谱由平台根据运行轨迹和结构化产出生成。

### R9. 最小人工确认

确认报告中的人工列固定为：

```text
人工结论 / 修改类型 / 修改内容 / 备注
```

人工结论初始为空，只允许：

```text
采纳 / 修改后采纳 / 删除
```

“修改后采纳”必须填写修改类型和修改内容；“删除”必须填写修改类型。存在未审核空白时可保存草稿，但不能进入 Skill 进化。

### R10. 人工补充文件

当人工需要补充完整方案、用例、执行证据或报告时，应在飞轮对应阶段独立上传，并绑定项目、流程、阶段和原始产出。上传文件不得自动成为金标或触发 Skill 发布。

### R11. 差异与归因

平台应结合原始产出、人工确认、补充文件和证据图谱生成结构化差异，并提出待确认归因。未经人工确认的归因不得用于生成 Skill 候选。

### R12. Skill 内容候选

系统应支持对 `SKILL.md`、相关 references、schemas、模板和确定性校验脚本生成最小增量补丁，并创建新的不可变 SkillVersion，不得覆盖 active 包。

### R13. 评测与晋级

候选与基线必须在相同冻结数据集和模型配置上对照。关键回归案例退化、schema 失败、隐藏集泄漏或未修复目标 Badcase 时必须阻止晋级。

### R14. 旁路产出纳管

从业务页面直接生成的产出应旁路沉淀但不影响受控门禁。用户可以显式纳入飞轮；纳管前必须校验项目、阶段、SkillVersion、父产出和冲突状态。

### R15. 失败补偿

业务生成成功与飞轮登记成功应分别呈现。飞轮写入失败不得造成业务产物丢失，必须进入幂等重试和死信告警。

## 4. 非目标

- 不重建第二套 Agent 或阶段业务逻辑。
- 不要求所有 Skill 一次性升级为 L3。
- 不把聊天草稿自动认定为正式阶段产出。
- 不把人工上传动作直接等同于金标确认。
- 不允许 AI 自动确认归因、激活候选或绕过人工审批。
- 不保存或展示模型隐藏思维链。

## 5. 一期范围

一期只完成上证 e 投票方案生成阶段：

1. 飞轮自动跳转方案分析；
2. 可信执行上下文和执行尝试；
3. Agent 运行状态与正式产出事件；
4. e投票方案 Skill 输出 `stage_result.json`；
5. 平台生成确认报告、质量摘要和首版证据图谱；
6. 三态人工确认与阶段补充文件上传。

用例、执行和报告适配器，以及完整 Skill 内容进化在后续批次完成。
