# 上证 e 投票全流程 Skill 数据飞轮需求

> 状态：待确认。本文只定义目标、边界和验收口径；技术设计与实施任务须在本需求确认后展开。

## 1. 目标

在不改变测试人员现有工作入口的前提下，让上证 e 投票全流程 Skill 形成可追溯、可评测、可回滚的迭代闭环：

`测试方案生成 → 测试用例生成 → 测试执行 → 测试报告生成`

平台支持两种互补的改进方式：

1. **历史回放对照**：使用历史需求及真实交付物，对同一输入重新生成并与历史方案、用例等基准产物进行结构化对比。
2. **在线人工反馈**：使用当前 Skill 生成阶段产物，人工评审、修改或标注后上传确认稿，形成可归因的反馈和候选优化点。

需求管理、LLM 对话、测试管理和数据飞轮页面只是不同入口；它们必须写入同一份飞轮账本，不得形成互不相认的任务记录。

## 2. 核心原则

### P1. 阶段独立进化，链路联合验收

- 四个阶段分别绑定 Skill 与版本，分别归因、评测和发布。
- 同一业务流程共享 `workflow_id`，通过 `parent_output_ids` 串联上下游。
- 除阶段指标外，还必须评估端到端结果，避免单阶段分数提升却损害整条链路。

### P2. 产出、反馈、金标、优化彼此分离

- 生成文件是 `GenerationOutput`，表示“系统当时产出了什么”。
- 人工确认稿、评分和处置是 `FeedbackEvent`，表示“人如何评价这份产出”。
- 经过复核、冻结的数据才是金标，不能把历史文档或一次上传直接当作绝对正确答案。
- 优化提案和 Skill 候选版本是受治理的派生结果，不得由上传反馈动作隐式激活。

### P3. 版本可复现

- 流程启动时一次性锁定四阶段 Skill 版本。
- 每份产出必须保存 Skill 版本、包哈希、模型、Prompt、输入快照哈希和上游产出。
- Skill 新版本激活不得改变运行中流程，也不得改写历史产出的归属。

### P4. 训练/改进数据与最终评测数据隔离

- 用于生成优化建议或派生候选版本的样本不得同时作为候选版本的隐藏验收样本。
- 数据集至少划分为 `gold`、`regression`、`fresh`、`challenge`、`hidden`。
- `hidden` 集的期望答案不得进入生成上下文、优化 Prompt 或人工候选说明。

### P5. 自动沉淀候选，受控晋级正式资产

- 平台应从历史回放、人工确认稿、缺陷确认、误报/漏报、生产回退和高价值边界场景中自动发现金标候选。
- “自动沉淀”默认表示自动采集、去重、分类、补齐来源和进入候选池；不表示未经门禁自动成为正式金标。
- 自动化只能生成候选、执行预检、去重、推荐分类和补齐元数据；任何资产进入金标主集、回归测试集、专用测试集或其他正式测试集前，都必须由人工审核确认。
- 来源完整、证据可定位、隐私合规且标注一致是“可提交人工审核”的前提，不构成自动晋级依据；有业务判断争议的候选必须人工复核或仲裁。
- 正式数据资产必须版本化、可冻结、可退役；新增样本只能形成后继版本，不得修改已用于历史评测的冻结版本。
- “上证 e 投票专用集”是业务范围维度；`regression`、`fresh`、`challenge`、`hidden` 是评测分区维度。二者不得混成互斥分类：同一案例可以属于上证 e 投票专用集，同时处于 `regression` 分区。

### P6. 质量飞轮按项目严格隔离

- Skill Hub 是全平台公开的 Skill 商店与版本库，项目成员可以浏览其中的 Skill 和版本。
- 每个项目拥有独立的产出、反馈、知识库、Skill 执行配置与版本锁、金标集、回归集、专用测试集、评测记录和发布状态。
- 项目在执行任务前必须从 Skill Hub 明确选择各阶段使用的 Skill 和具体版本；选择结果只对当前项目/流程生效，不改变 Skill Hub 的全局条目或其他项目的选择。
- 所有飞轮资产必须带不可为空的 `project_id`；任何读写、检索、去重、评测、优化、审批和运行时解析都必须先限定项目范围。
- 不同项目可以选择同一公开 Skill 的不同版本；其任务锁、反馈、候选优化、评测结果和发布决策必须彼此隔离，不得交叉归因。
- 跨项目复制或复用必须是显式、受权限控制且可审计的导入动作，并在目标项目生成独立副本；不得保留对源项目私有资产的运行时依赖。
- 公开 Skill 可被项目显式选择并锁定；公共知识模板仍须明确导入项目。项目反馈不得直接改写公开 Skill，优化结果先形成候选版本，经过治理后才能进入 Skill Hub。

## 3. 用户流程

### 3.1 历史回放对照

测试负责人创建“历史回放批次”，上传或选择：

- 原始需求文档及其版本；
- 历史真实测试方案；
- 历史真实测试用例；
- 可选的执行记录、缺陷记录和测试报告；
- 业务模块、需求类型、风险等级、适用版本等元数据。

系统为每个阶段生成“参考答案候选”，经人工确认后进入相应金标集。随后用指定 Skill 版本重放，并输出结构化差异、评分和可验证的候选优化点。

### 3.2 在线人工反馈

测试人员从任一现有入口发起任务，平台自动携带飞轮上下文。阶段完成后，用户可下载原始产物，人工修改或打标签后上传确认稿。

系统应：

1. 校验上传文件与项目、流程、阶段及原始产出匹配；
2. 解析采纳、删除、修改、补充及无法判断项；
3. 只记录反馈，不自动改包；
4. 由 AI 基于差异、证据和当前 Skill 包提出候选优化点；
5. 由人工逐条采纳、改写或驳回；
6. 以已确认优化点派生新的 Skill 候选版本；
7. 在隔离评测集上完成基线/候选对照后进入审批。

### 3.3 跨入口联动

支持以下入口：

- 需求管理中的需求文档或拆解结果；
- LLM 对话中调用阶段 Skill；
- 测试管理中的用例生成与测试执行；
- 数据飞轮中的历史回放或全链路流程。

所有入口统一携带 `FlywheelContext`：

- `project_id`
- `workflow_id`
- `stage`
- `capability_id`
- `skill_version_id`
- `requirement_document_ids`
- `parent_output_ids`
- `entry_type`
- `evaluation_intent`（普通生产、历史回放、影子评测）

普通聊天不强制进入飞轮；一旦用户选择“关联飞轮流程”，后续阶段不得依靠用户反复手填 `workflow_id`、`module_key` 或上游产出 ID。

### 3.4 自动数据资产沉淀

每次正式阶段产出及后续反馈完成后，平台自动运行候选提取：

1. 判断来源、证据、隐私和是否允许用于优化；
2. 按需求版本、业务规则、输入输出哈希和语义相似度去重；
3. 识别样本价值：关键业务、历史缺陷、漏测、误报、边界、异常、兼容性或普通覆盖；
4. 自动推荐业务专用集和评测分区，但保存推荐依据与置信度；
5. 所有候选进入人工审核队列，由审核人确认内容、归属、分区和适用范围；
6. 审核通过后才可创建新的冻结数据集版本，供后续回放和候选版本门禁使用。

平台至少维护三类可组合资产视图：

- **金标主集**：跨版本复用的已确认输入、期望输出、评分规则和证据；作为事实基准，不等同于某一次测试任务的原始交付物。
- **回归测试集**：由已修复缺陷、历史漏测、误报、Skill 回退原因和关键规则沉淀；每个案例必须记录“防止哪类问题复发”，候选 Skill 每次晋级必须全量执行。
- **上证 e 投票专用测试集**：按业务域组织，覆盖投票创建、权限与身份、股东大会、议案、表决、结果统计、异常与边界、兼容性等专用场景；可进一步按阶段和业务模块形成子集。

## 4. 验收需求

### R1. 历史样本导入与质量控制

- 当用户上传一组历史资料时，系统应按“一个需求版本 + 各阶段真实产物”建立样本包，并保留原始文件哈希。
- 当需求与真实产物无法可靠匹配时，系统应将样本标记为待核对，不得自动进入评测集。
- 当历史产物被人工确认存在遗漏或错误时，系统应允许形成修订后的期望输出，并同时保留原始交付物。
- 当样本包含敏感账号、证书、个人信息或生产数据时，系统应在进入模型前执行脱敏或禁止优化。

### R2. 历史回放

- 当回放任务启动时，系统应锁定待评测的四阶段 Skill 版本和模型配置。
- 当某阶段完成时，系统应保存生成产物、结构化元素及其与历史基准的对应关系。
- 当回放失败或部分完成时，系统应保留已完成阶段，不得把部分结果伪装成完整链路评分。
- 当同一回放使用相同输入、Skill 包和模型参数重试时，系统应保留独立运行记录并标记重试关系。

### R3. 结构化比较与评分

- 测试方案比较至少覆盖需求范围、测试策略、风险、测试类型、资源、里程碑和退出准则。
- 测试用例比较至少覆盖需求/风险覆盖、正常/异常/边界场景、前置条件、步骤、数据和预期结果。
- 测试执行比较至少覆盖执行覆盖率、结果真实性、失败证据及缺陷关联。
- 测试报告比较至少覆盖范围、结果汇总、遗留风险、缺陷状态和发布结论。
- 系统不得用单一文本相似度决定优劣；每个分数必须能下钻到具体缺失、误增或冲突项。
- 当历史基准自身存在争议时，该项应进入人工仲裁，不得直接计为候选版本错误。

### R4. 在线反馈

- 当用户上传确认稿时，系统应验证它属于当前项目、流程、阶段和原始产出。
- 当确认稿被重复上传且文件哈希相同时，系统应返回原反馈，不重复计数。
- 当用户只想记录反馈时，系统不得自动派生或激活 Skill 版本。
- 当反馈缺少可定位证据时，可记录为意见，但不得自动进入金标或优化输入。

### R5. 候选优化与人工确认

- AI 生成的优化点必须处于 `proposed` 状态，且带来源差异、影响阶段、预期收益和潜在副作用。
- 人工必须能逐条采纳、改写或驳回，并记录操作者、时间和理由。
- 未经人工确认的 AI 假设不得用于派生 Skill 候选版本。
- 候选修改应优先形成最小增量补丁；不得无理由重写整个 Skill 包或覆盖业务模板。

### R6. 评测、防泄漏和晋级

- 候选版本应与当前生产基线在同一冻结数据集版本和模型配置上对照。
- 门禁至少包含质量变化、关键项零退化、延迟、Token/成本和格式契约。
- 优化使用过的样本不得计入隐藏集最终成绩。
- 当候选只改善平均分但导致任一关键业务场景退化时，系统应阻止晋级。
- 只有评测通过并经负责人审批的版本才能激活；激活后必须支持观察与回滚。

### R7. 对话入口联动

- 当用户从需求文档进入 LLM 对话并选择关联飞轮时，系统应自动创建或选择流程、识别当前阶段并锁定 Skill 版本。
- 当 Agent 正式提交阶段产出时，系统应写入统一产出协议；草稿聊天消息不得自动当作正式阶段产出。
- 当阶段产出提交后，下一阶段应自动继承上游产出和需求上下文。
- 当对话未提供飞轮上下文时，界面应明确显示“未纳入飞轮”，不得静默产生无法归因的数据。

### R8. 测试管理入口联动

- 当用户从测试管理生成用例或执行用例并关联飞轮时，系统应自动继承 `workflow_id`、阶段和 `source_output`。
- 当测试执行结束时，系统应将结果回写 `test_execution` 阶段，并关联实际执行的用例版本。
- 当测试人员从测试管理创建或维护 Skill 时，系统应进入 Skill 版本治理流程，而不是直接覆盖生产 Skill。

### R9. 可观测与审计

- 任一产出应能追溯输入文档、上游产出、Skill 包、模型、Prompt、工具调用、检索引用、反馈、金标和后继版本。
- 项目成员只能读取本项目数据；导出、金标冻结、候选审批和激活必须留审计记录。
- 飞轮写入失败不得改变原业务任务结果，但必须产生可检索的补偿任务和告警；不能仅记录日志后永久丢失。

### R10. 金标候选自动沉淀

- 当正式阶段产出收到人工确认、缺陷确认、误报、漏报、测试失败或生产回退信号时，系统应自动生成或更新金标候选，并关联原产出、反馈、Skill 版本和证据。
- 当候选缺少输入快照、期望输出、评分规则、来源证据或隐私声明时，系统应保持候选状态并列出缺失项，不得自动晋级。
- 当候选与现有案例输入和期望语义等价时，系统应合并为同一案例的新增证据或出现次数，不得简单复制成多个案例。
- 当候选与现有案例输入相近但期望冲突时，系统应创建冲突记录并进入仲裁，不得以最新上传覆盖旧结论。
- 当候选通过自动预检时，系统应将其提交人工审核并展示来源、证据、差异、推荐归属和风险；不得自动确认或自动写入正式测试集。
- 当人工审核候选时，审核人应能批准、修改后批准、驳回或转交仲裁；系统必须记录审核人、时间、结论和理由。
- 当候选未经人工审核确认时，系统不得将其用于 Skill 晋级门禁、回归结论或正式覆盖率统计。

### R11. 回归测试集

- 当缺陷被确认并完成修复复测、漏测被补齐、误报规则被纠正或 Skill 版本发生回滚时，系统应自动推荐生成回归案例。
- 每个回归案例必须包含失败前表现、正确期望、触发条件、来源版本和防复发目标。
- 当候选 Skill 发起晋级评测时，系统应全量运行适用的回归案例；任一标记为关键的回归案例退化时，系统应阻止晋级。
- 当业务规则失效或适用版本结束时，回归案例应进入退役流程，不得直接删除历史记录。

### R12. 上证 e 投票专用测试集

- 当金标候选被识别为上证 e 投票业务场景时，系统应依据业务模块、测试阶段、风险等级、规则版本和适用环境自动推荐专用集标签。
- 当同一案例同时属于专用业务范围和回归用途时，系统应通过“数据集归属 + 评测分区/标签”组合表达，不得复制两份内容。
- 当发起上证 e 投票 Skill 评测时，系统应支持选择完整专用集或按模块、阶段、风险和规则版本筛选子集。
- 专用集必须保留关键业务场景清单与覆盖率；当清单存在未覆盖项时，系统应阻止将该数据集标记为“覆盖完整”。
- 专用集中的隐藏分区必须与优化输入隔离，且只有评测服务可读取期望答案。
- 上证 e 投票首版业务分类、关键场景清单及后续变更由测试负责人维护并审批；其他人员可提交候选，但不得直接修改已发布分类或把覆盖状态标记为完整。

### R13. 项目级资产隔离

- 当用户进入质量飞轮时，系统应只展示当前项目的产出、反馈、Skill 选择与版本锁、知识库、金标集、回归集、专用集、评测和发布记录；进入 Skill Hub 时可浏览公开 Skill 商店及其版本。
- 当创建、上传、导入、检索、去重、评测、派生、审批、激活或回滚任一资产时，系统应校验该资产及其全部关联对象属于同一项目；发现跨项目引用时必须拒绝并记录审计事件。
- 当不同项目选择同一 Skill 或不同版本时，系统应保持各自独立的任务锁、反馈、金标、评测和执行配置；项目操作不得改变其他项目已锁定或待执行的版本。
- 当项目删除、归档或成员权限变化时，系统应按项目数据治理策略处理其飞轮资产，不得影响其他项目或公共模板。
- 当用户显式执行跨项目导入时，系统应要求源项目读取权限和目标项目管理权限，展示将复制的资产范围，并在目标项目重新执行隐私检查与人工审核。

## 5. 非目标

- 不把飞轮建设为替代需求管理、LLM 对话或测试管理的新工作台。
- 不在没有人工确认与门禁的情况下自动改写、发布 Skill。
- 不把所有对话消息、历史文档或人工上传文件自动视为训练数据。
- 不在本期训练基础模型；优化对象为 Skill 包、Prompt、模板、规则、检索配置和工具配置。
- 不将上证 e 投票业务专属字段写死在公共飞轮协议中；专属内容通过结构化扩展和阶段评测器承载。

## 6. 完成定义

- 一份历史需求可连同历史方案和用例导入、核对、冻结并完成至少一次基线/候选回放。
- 一条在线四阶段流程可从需求管理或 LLM 对话发起，并在测试管理继续执行，无需手工复制流程标识。
- 四阶段产出均绑定准确 Skill 版本和上下游血缘。
- 人工确认稿可形成反馈、候选优化点和受治理的 Skill 候选版本。
- 评测可证明不存在样本泄漏，并能解释候选版本为何通过或未通过。
- 飞轮可自动生成金标候选，并受控沉淀为版本化金标主集、回归测试集和上证 e 投票专用测试集。
- 所有正式测试集资产均经过人工审核确认，自动化不会越过审核门禁。
- Skill Hub 公开共享；不同项目的 Skill 选择/版本锁、知识库、金标集、测试集、反馈和评测记录相互隔离，私有资产跨项目复用只能显式导入。
- 候选 Skill 晋级时会强制运行适用回归集，并支持按业务模块运行专用测试子集。
- 任一候选版本均可审批、激活、观察和回滚，历史产出归属不随当前版本变化。

## 7. 待确认业务决策

5. 生产流程上传确认稿后，是只形成反馈，还是允许负责人一键进入候选优化向导？
