# 代码审查正常变更与真实缺陷区分：需求

## 背景与目标

sseWebVote 报告把正常的 `@NotNull` 移除、请求字段改由登录上下文取得、环境变量新增等变化列为待确认高风险；同一改动被规则和 AI 重复报告。反证模型两批失败后，未经核实的候选仍沿用初始高风险等级。目标是减少这类误报，同时保留真正误删权限、校验、事务及关键配置的发现能力和全部文件审查覆盖。

## 验收标准

1. 当规则扫描发现注解、装饰器、修饰符或配置行被删除时，系统应对齐同一代码元素或配置键的新旧实现，并记录“实质删除 / 同处替换 / 迁移到其他位置 / 无法判断”及证据；仅凭删除行不得给出确定缺陷或高影响结论。
2. 当目标版本存在同一职责的等价保护或配置迁移时，系统应排除对应候选，或在等价性仍依赖运行环境时列出具体待确认条件；不得继续描述为“删除即失效”。
3. 当保护确实消失且存在可达触发路径与可验证错误结果时，系统应保留缺陷，并按实际影响定级；不得因降低误报而屏蔽真实误删。
4. 当 AI 将正常新增功能、配置或“若配置错误可能失败”写成风险时，系统应将其与明确的目标版本错误区分；纯假设和普通测试建议不得进入待确认高风险。
5. 当用户关联需求、接口或业务文档时，系统应在反证阶段检索与候选相关的片段，注明文档标题、版本或解析状态，并将文档作为业务意图证据；文档不得代替目标代码、调用链或运行时证据，也不得因旧文档压过新代码。
6. 当反证模型失败、超时或候选未进入反证批次时，系统应显式标记“核验未完成”及原因；仅有规则命中或 AI 假设的候选不得沿用无证据的高风险等级，也不得变成确定缺陷。真正具有直接证据的候选仍应保留。
7. 当规则与 AI 报告同一代码元素和同一失效机制时，报告应归并为一项并保留来源证据；不同字段、触发条件或失效机制不得仅因标题相似被合并。
8. 报告应分别展示候选来源、替换/迁移证据、反证状态、缺少的确认信息和风险定级依据；审查覆盖率不得因为排除误报而降低。

## 回归样本

- 正常变更：sseWebVote 报告中的六项待确认高风险不应继续作为高风险交付。
- 正例：有可达接口的权限注解误删、必填校验误删且无替代、关键配置删除且运行时无有效值，应保持可报告。
- 降级：反证服务返回 500、仅部分批次完成、无业务文档、文档版本过期时，状态与定级应符合上述规则。

## 非目标

- 不通过单纯降低全部规则严重度或减少扫描文件数来改善误报率。
- 不把业务文档的“符合预期”自动等同于代码正确。
- 本期不更改历史报告或用户已确认的草稿记录。
