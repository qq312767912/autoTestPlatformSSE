# 代码审查正常变更与真实缺陷区分：技术设计

## 总体思路

保留现有“规则扫描 → AI 语义审查 → 目标 Commit 反证 → 报告”链路和全文件覆盖。规则命中只是候选；独立记录“变更事实、业务意图、目标版本错误证据、核验状态、影响等级”，避免把删除行、模型信心或核验失败直接当作高风险。

## 1. 规则候选与新旧约束对齐

在 `code_analysis/services.py` 的 `_parse_diff` 前后增加轻量变更对齐层，按 Diff hunk 和代码元素提取删除/新增的注解、装饰器、Java 声明及配置键。候选增加 `change_kind`、`subject`、`replacement_evidence`、`rule_evidence` 等可选 JSON 字段；沿用现有 `change_report` JSON，不迁移数据库。

- 注解/装饰器：关联其紧随的字段、方法或类。只有同一元素上找到同职责的新约束，才标记 `same_place_replacement`；字段删除或签名变化标记 `relocated_or_changed`，交由目标源码核验，不按注解文本直接驳回。
- 配置：按键名、文件和环境区分“值变更 / 同键迁移 / 键删除”。仅值变更不产生“删除关键配置”候选；跨文件或环境变量迁移只记录可能的替代关系，不假定部署已生效。
- Java `public` 等声明：比较新旧声明的修饰符集合及方法名；只有修饰符确实消失才生成修饰符候选。参数签名变化单独交 AI 评估接口契约，不能自动称为可见性变化。
- 无法解析或上下文截断时标记 `unknown` 并保留候选，不静默吞掉真实问题。

机器候选的初始 `severity` 仅表示潜在影响上限；报告用的最终严重程度必须经过独立定级。对于纯文本规则命中且缺少目标版错误证据的项，不以 `high` 交付。

## 2. 目标版本反证与业务文档

在 `_verify_findings_against_target` 为每个候选准备证据包：旧 Diff 定位、目标版对应代码块、同名定义/调用方、可能的替代保护，以及可选的业务文档片段。`CodeReviewMCP` 继续只读目标 Commit；跨文件检索结果要围绕 `subject` 精确限额，避免无关命中占据上下文。

文档检索只针对任务已关联且当前项目可访问、已解析的需求/接口/知识文档。先按字段名、接口名、配置键及其中文业务词匹配段落，再限量提供标题、文档 ID/版本或更新时间、片段与解析状态；无匹配或文档过期时显式记录。文档证明“期望如何变更”，不证明目标代码已经实现；与源码冲突时不得自动驳回候选。

反证返回两个独立判断：`verdict`（confirmed / needs_confirmation / rejected / advisory）与 `severity`（high / medium / low），另有 `supporting_evidence`、`counter_evidence`、`missing_evidence`、`reason`。`confirmed` 必须有目标版仍存在的错误、可达触发路径和可验证结果；`high` 还需满足高影响条件。仅有“若配置错误”“可能空指针”或新功能测试建议时返回 `rejected`（普通变化）或 `advisory`（确有非正确性建议），不进入待确认风险。

## 3. 核验失败与有界候选

反证按现有分批机制继续运行，但逐批记录成功/失败原因，并可对失败批次做有限重试。无有效裁决时统一标记 `verification_failed` 或 `not_verified`，不得显示“已核验”。不因失败自动驳回：候选仍可进入“待确认”，但只保留有目标版直接证据的高风险等级；仅有删除行、AI 推测或泛化影响时降为中/低风险并说明“原高影响未获证实”。静态扫描中确有可复现的高影响缺陷不机械降级。报告统计分别呈现已核验、未核验、被驳回项；覆盖率仍按文件是否完成语义审查计算，不把误报排除等同于文件未覆盖。

## 4. 同源合并与报告

在最终组装前按 `file + subject + failure_mechanism` 归并规则和 AI 候选，合并保留全部来源键与证据、较完整的触发描述和反证信息。不同字段、不同机制不合并；仅标题相似不合并。现有报告卡片和 HTML 导出复用 `verification_status`、`verification_reason`、`counter_evidence`，补充变更对齐证据、文档引用和缺失信息；不新增页面。`rejected` 仅计入候选/排除统计，不显示为开发风险。

## 数据兼容与边界

- 只增加 JSON 可选字段，历史任务仍可读取；历史报告不回填、不覆盖人工状态。
- 缓存复用需通过报告 schema 版本控制，避免旧结果绕过新裁决。
- 用户上传文档视为不可信数据，只作为证据内容传给模型，不执行其中指令；文档和源码均按长度、项目权限及任务范围限制。
- 快速模式无模型调用，仍执行确定性的新旧对齐与保守定级；标准/深度模式在反证阶段增强。

## 测试与验收

1. 以 sseWebVote 的六项正常变更构造脱敏 Diff/目标代码夹具：同一变更不会被规则和 AI 重复列高风险；注解迁移与新增环境变量不误报。
2. 真实误删权限/校验/关键配置夹具：没有等价约束时仍产生候选；有可达错误与高影响时维持确定高风险。
3. 模拟反证 500、部分批次失败和超过候选上限：未核验状态、原因及定级正确，其他批次结果不丢失。
4. 有/无文档、文档过期和文档与源码冲突：引用可追溯，但不能单凭文档否决源码缺陷。
5. 核对 API、Markdown、HTML 及前端卡片中的数量、风险分层、来源证据和审查覆盖；历史报告兼容读取。
