# 生产级质量自进化与 Skill Hub - 需求规格

## 1. 问题与目标

当前平台已有产出采集、金标、评测、归因、优化候选和受控发布的公共底座，但尚未将真实业务能力、Skill 包、评测版本和生产运行版本连成可审计闭环。

本需求将建设两类受控自进化能力：

1. **Skill 能力自进化**：用例审查、测试方案、测试用例、测试执行和报告生成必须绑定可版本化 Skill，支持失败归因、候选版本、影子评测、人工审批、激活和回滚。
2. **复合能力自进化**：代码审查不得伪装成 Skill。它应独立版本化和优化 Prompt、机器规则、检索/CRG 策略、反证核验策略及工具配置，再以一个代码审查能力版本聚合发布。

自进化始终是受控流程，不允许候选内容绕过评测和人工审批自动进入生产。

## 2. 范围

### 2.1 Skill 型能力

- 用例审查 `case_review`：单次评测、独立进化。
- 测试方案 `test_plan_generation`：全链路测试第一阶段。
- 测试用例 `testcase_generation`：全链路测试第二阶段。
- 测试执行 `test_execution`：全链路测试第三阶段。
- 报告生成 `report_generation`：全链路测试第四阶段。

四阶段主门禁固定为：

`test_plan_generation -> testcase_generation -> test_execution -> report_generation`

风险识别、问题跟踪、知识问答保留为反馈、归因或单次评测数据源，不冒充四阶段 Skill 主链路。

### 2.2 复合能力

- 代码审查 `code_review`：单次评测与复合发布，不属于 Skill Hub 包管理。
- 可进化子单元：Prompt、机器规则集、CRG/检索策略、反证核验策略、工具参数。
- 发布时组合为不可变的复合能力版本，并保存所有子单元哈希。

## 3. 用户角色

- **测试负责人**：管理能力绑定、启动评测、审批发布、激活、回滚和隔离。
- **测试执行人员**：上传候选 Skill、触发验证、查看评测和提交反馈，不能直接激活生产版本。
- 项目 Owner/Admin/Member 是基础权限来源，不在 Skill Hub 中作为业务角色展示。

## 4. Skill Hub 包与版本管理

### R1 包上传与安全校验

- 当用户上传 ZIP 时，系统应校验路径穿越、符号链接、文件数、解压体积、包哈希、`SKILL.md` frontmatter 和 UTF-8 编码。
- 当包缺少版本、入口、能力阶段或输入/输出 Schema 时，系统应将其标记为校验失败，不允许进入影子评测。
- 当包含有密钥、Token、Cookie 或明文凭据时，系统应拒绝入库并返回可定位的安全问题。
- 当同一 Skill 的同一版本和包哈希重复上传时，系统应幂等返回已有版本，不重复创建。

### R2 不可变版本与生命周期

- Skill 逻辑名称与 Skill 版本必须分离存储。
- 已入库的版本包不得原地覆盖；任何内容变化必须产生新版本和新 SHA-256。
- 版本状态应支持：`draft`、`validating`、`shadow`、`awaiting_approval`、`active`、`retired`、`rejected`、`rolled_back`、`quarantined`。
- 一个项目的同一 Skill 在任意时刻只能有一个 `active` 版本。
- 当候选版本被激活时，系统应将旧活跃版本标记为 `retired`，并保留可回滚链路。

### R3 Skill 下载与可复现性

- 当有权用户下载 Skill 版本时，系统应生成内容稳定的 ZIP 包，并返回文件名、版本及 SHA-256。
- 导出包应保留 `SKILL.md`、脚本、模板和非敏感配置，并排除 API Key、登录态、运行日志、缓存、产物和密文文件。
- 导出包重新上传后，系统应能恢复相同的包哈希和运行定义。
- 下载操作必须记入审计日志。

### R4 能力绑定

- 当 Skill 版本进入评测时，系统应将其绑定到 `CapabilityDefinition`，并记录支持的阶段、评测模式、默认评测集和门禁规则。
- 当业务调用 Skill 时，运行时应解析当前活跃 Skill 版本，并把 `skill_id`、`skill_version_id`、`capability_id` 和包哈希写入统一产出协议。
- 当一次任务已开始时，该任务必须锁定启动时版本，中途激活新版本不得改变已在运行的任务。

## 5. 自进化闭环

### R5 反馈与金标

- 当产出被采纳、驳回、人工编辑、测试验证、确认缺陷、标记误报或漏报时，系统应将反馈精确绑定到产出和生成它的版本。
- 当 Badcase 证据完整且经负责人复核时，系统应允许将其升级为按能力和版本分类的金标资产。
- 当反馈无证据、来源不可追溯或包含禁止入模数据时，系统不得自动生成优化候选。

### R6 归因和候选生成

- 当评测或真实结果失败时，系统应生成到意图、规划、Prompt、知识、检索、Skill/工具、执行环境和下游结果的多层归因。
- 当归因尚未人工确认时，系统应允许查看假设和反证，但不得生成可发布版本。
- 当确认为 Skill 指令、脚本、模板或允许配置问题时，系统应从旧版本派生新候选版本，不得原地编辑活跃版本。
- 当候选包产生时，系统应输出可阅读 diff、变更原因、预期收益、影响范围和回滚目标。

### R7 评测、门禁和发布

- 当候选版本完成静态校验后，系统应使用金标、回归、新鲜、挑战、隐藏集执行影子评测。
- 当候选版本的质量、漏报、误报、耗时或 Token 回归超过门禁时，系统应阻止提交审批。
- 当所有硬门禁通过时，系统应将候选置为 `awaiting_approval`，而不是自动激活。
- 当测试负责人审批后，系统应原子切换活跃版本，并记录审批人、评测快照、旧版本和回滚点。
- 当生产观察窗口突破已配置阈值时，系统应自动回滚到上一活跃版本，并发出告警。

### R8 全链路测试

- 当测试方案开始时，系统应创建稳定 `workflow_id`，并锁定四个阶段的 Skill 版本。
- 当前一阶段门禁未通过且未被负责人留痕放行时，系统应拒绝启动后一阶段。
- 当下游失败时，系统应沿 `parent_output_ids` 将责任反向归因到产生错误的上游 Skill 版本。
- 当仅某一阶段 Skill 发生改变时，系统应同时执行该阶段独立评测和四阶段端到端评测。

### R9 代码审查复合能力进化

- 当代码审查出现误报、漏报或人工编辑时，系统应将反馈绑定到本次复合能力版本。
- 当归因为 Prompt、机器规则、CRG/检索、反证核验或工具配置问题时，系统应只生成对应类型的子单元候选。
- 当组合候选进入影子评测时，系统应保持全部 Diff 文件审查，不得以减少覆盖换取速度或采纳率。
- 当候选通过时，系统应发布包含所有子单元版本和哈希的新复合能力版本，而不是 Skill 包。

## 6. Skill Hub 界面需求

### R10 信息架构

Skill Hub 应在一个页面提供：

1. **Skill 目录**：按业务阶段、状态和项目筛选。
2. **版本详情**：包哈希、创建人、来源、Schema、依赖、变更 diff 和下载。
3. **评测与门禁**：基线/候选对比、金标分区、质量、耗时、Token、漏报和误报。
4. **发布治理**：提交审批、激活、驳回、隔离、回滚和审计时间线。
5. **能力绑定**：显示该 Skill 被哪些单次能力或四阶段流程使用。

### R11 上传下载交互

- 当用户点击上传时，页面应先展示包校验结果，再允许保存为候选版本。
- 当用户点击下载时，页面应明确展示导出版本和哈希，并下载服务端生成的脱敏 ZIP。
- 当候选没有评测集或未通过门禁时，发布操作应禁用并展示缺失条件。

## 7. 权限、审计与安全

### R12 权限和审计

- 上传、下载、校验、评测、提交审批、激活、驳回、回滚和隔离均必须写入审计日志。
- 当用户尝试访问其项目之外的 Skill 包、评测结果或下载链接时，系统应返回 403，不得泄露元数据。
- 当 Skill 来自上传、Git 或远程商店时，系统应保存来源、提交号/校验和、上传人和时间。
- 当包处于 `quarantined` 或 `rejected` 时，任何业务运行时不得加载它。

## 8. 数据迁移与兼容

### R13 现有 Skill 迁移

- 当迁移现有 `Skill` 记录时，系统应为每条记录生成初始不可变版本，计算包哈希，并保留原有业务调用兼容。
- 当旧业务仅传递 `skill_id` 时，运行时应解析该 Skill 的**可运行版本**；当没有任何可运行版本时，应明确拒绝执行而不是静默使用未版本化文件。
- 迁移过程不得删除原 Skill 文件或改变当前业务结果。

#### R13.1 解析口径修订（2026-10-02，T25）

> 原文（已作废）："运行时应解析该 Skill 的**活跃版本**；当没有活跃版本时，应明确拒绝执行。"
>
> **本条真正的意图是"不得静默使用未版本化文件"**——必须落到某个不可变版本包上。这一点不变。
> "必须活跃"是当初的错误实现：**激活只是可选的钉版手段**（把生产版本钉在某一版），不是可用性前提。
> 上传 / Git 导入 / 商店导入三条通道在落盘前都已跑过同一套静态校验，
> 所以"没激活"只意味着"还没人指定生产版本"，**不构成拒绝理由**。

现行判据（**唯一真值** = `skills/models.py::UNRUNNABLE_RELEASE_STATES` + `SkillVersion.is_runnable`）：

```python
UNRUNNABLE_RELEASE_STATES = ('quarantined', 'rejected')

is_runnable == skill.is_active and package_path != '' and state not in UNRUNNABLE_RELEASE_STATES
```

- 用**排除法**而不是"枚举所有可用状态"：新增发布状态时不会因为漏列而被静默误拒。
- `package_path` 空 = 迁移生成的"只留内联 `SKILL.md`"记录（`manifest.needs_package_rebuild`），
  运行时读不到任何文件，**必须保持不可运行**。
- 解析优先级（`SkillRuntimeResolver.runnable_version`）：**活跃版本优先（若可运行且阶段匹配），
  否则取最新可运行版本**。保留"活跃优先"是为了不让派生候选因"更新"自动生效。
- `resolve_version` / `runnable_version` / `stage_catalog` 全部共用这一处判据，**判据只能有一处定义**。

仍未放宽的部分：**锁定的版本必须来自不可变版本包**（`WorkflowSkillLock` 仍按 `skill_version_id` 落库），
历史链路依然读锁定版本、不读"当前活跃版本"；自进化派生仍要求**基线是当前活跃版本**。

## 9. 非功能需求

- Skill 版本解析 P95 小于 50ms，不包含 Skill 本身执行时间。
- 下载包必须以流式响应生成，不得将整包长期复制到临时公共目录。
- 并发激活同一 Skill 时必须通过事务和数据库约束保证唯一活跃版本。
- 飞轮记录失败不得改变原业务任务结果；但生产 Skill 版本解析失败必须阻止新任务开始。
- 所有新接口必须具备项目隔离、幂等、权限和失败分支自动化测试。

## 10. 完成定义

1. 五个 Skill 型能力的真实业务产出都锁定 Skill 版本并关联能力定义。
2. 全链路测试实际执行四阶段门禁，并能反向归因上游版本。
3. 代码审查以复合能力版本而非 Skill 版本完成候选、影子评测、审批、激活和回滚。
4. Skill Hub 支持 ZIP 上传、Git/商店导入、脱敏 ZIP 下载、版本查看、diff、评测、审批、激活和回滚。
5. 所有候选都经过金标/回归/挑战/隐藏/影子评测，未通过时无法发布。
6. 上传、下载、审批、激活和回滚有完整审计。**（2026-10-02 / T27 修订，同日两次）**：Skill Hub 是**平台级公共目录**，条目不属于任何单一项目，所以访问边界按**角色**判定而不是按 URL 项目 —— 读（列表/详情/内容/版本史）任何登录用户可读；治理（补填阶段/启停/删除/隔离版本）需超管或任一项目测试负责人；创建类动作（上传/预检/候选/导入）仍锚定 URL 项目（"上传出处"）。⚠️ 初版只放开读侧、写侧仍按项目过滤，导致"列表能返回全平台 20 张卡、卡片上的按钮却一律 404"（实测项目 3 的 URL 下 20/20 张全死），已修正。
7. 完成后通过后端、前端、迁移、安全和真实链路验收，并在任务文档中记录验证结果。

## 11. 非目标

- 不允许 LLM 或 Agent 在无人审批时自动修改并发布生产 Skill。
- 不将代码审查打包成 Skill。
- 不在导出包中携带密钥、登录态、业务数据、金标数据或运行日志。
- 不通过减少代码审查 Diff 覆盖或测试覆盖换取更高的通过率。
