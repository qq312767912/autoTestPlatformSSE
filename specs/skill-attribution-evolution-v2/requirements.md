# Skill 自进化 V2 需求

## 1. 问题与目标

当前用例审查自进化主要把人工结果映射成 `prompt_error` 或
`generation_error`。这两个标签只说明“结果错在哪一层”，不足以回答：

- 错误的具体成因是什么；
- 证据来自哪个运行节点；
- 应修改 Skill、Prompt、Few-Shot、Tool Schema 还是 RAG；
- 修改的影响范围和回归风险是什么。

V2 目标是把“报告结果标签”升级为“可证明、可确认、可生成最小补丁、
可回归验证”的 Skill 持续进化闭环。

## 2. 范围

### 2.1 本期必须实现

1. 三元组归因：一级大类、二级细分标签、目标修复层级/动作。
2. 原有 `prompt_error / generation_error` 保留为原始失败信号，不再作为最终优化分类。
3. 候选归因必须关联可核验的证据引用，无证据不得进入候选修改。
4. 人工可对归因执行采纳、重新标注、驳回，只有采纳/重新标注的归因能生成补丁。
5. 根据修复层级生成定向候选：Skill SOP、Prompt、Few-Shot、Tool/Workflow、Knowledge/RAG。
6. 候选必须包含最小 diff、修改理由、证据、影响面、Token/公共能力风险。
7. 基于当次审查选中并实际执行的精确 Skill 版本派生试验版，不修改当前活跃包。
8. 为同一基线自动派生隔离的 A/B 试验分支（如 `skill@v1.2-exp.A/B`）。
9. 调用预置 `skill-creator` 生成 Skill 结构优化变体，能够注入前置检查、分步拆解、分支 SOP 与兜底流。
10. 默认生成至少两个变体：A 为最小扰动，B 为结构化优化；两者并行进入评测。
11. Prompt、Few-Shot、Tool/Workflow、Knowledge/RAG 均需生成可执行的隔离试验变体，并保留基线快照与回滚点。
12. 本期回归闸口以“Baseline/A/B 分别重跑本阶段 + 人工对比确认”为准。
13. 发布前必须人工确认胜出变体的 diff 与本阶段回归结果，通过后才能归档至 Skill Hub。

### 2.2 后续阶段

- 黄金数据集全量回归、自动 A/B 指标对比。
- 评测报告自动聚合（Old vs New、解决/未解决/退化用例清单）。

> 其余方案内容均属于本期。运行证据包含可审计的决策轨迹，
> 但不对外暴露模型隐藏思维链；以决策摘要、工具调用、检索和输出对比实现等价审计。

## 3. 归因分类契约

| 一级大类 | 二级标签 | 默认修复层级 |
| --- | --- | --- |
| `prompt_rules` 规则/指令漏洞 | `format_protocol_violation`、`required_field_missing`、`boundary_uncovered`、`instruction_priority_ambiguity` | Prompt / Skill SOP |
| `context_rag` 上下文与记忆 | `history_truncated`、`retrieval_noise`、`critical_context_missed` | Context / RAG |
| `tools_logic` 工具与逻辑 | `invalid_tool_argument`、`tool_api_failure`、`tool_chain_step_skipped` | Tool Schema / Workflow / Code |
| `domain_knowledge` 知识与语义 | `terminology_mismatch`、`private_semantic_drift` | Knowledge / Few-Shot |
| `skill_schema` Skill 结构缺失 | `precheck_missing`、`branch_sop_missing`、`guided_instruction_missing`、`fallback_missing` | Skill SOP |

允许人工重新标注。修复层级不得只由一级类别硬编码推导，必须与实际证据一起存储。

## 4. 证据契约

每个候选归因至少必须有一条证据，证据类型包括：

- `input_snapshot`：用户输入与必要上下文快照；
- `decision_summary`：可审计的决策节点摘要，不存储隐藏 CoT；
- `tool_call`：工具名、参数、结果/错误的引用；
- `retrieval_hit`：检索文档、分块、分数、排序的引用；
- `output_comparison`：实际输出、人工期望/修改结果的差异；
- `report_row`：已确认报告的 Sheet、行号、用例号、人工原因。

证据须保留来源 ID/指纹与可阅读摘要；大 Payload 使用引用而非重复嵌入。

## 5. 用户故事与验收标准

### R1：结构化归因

**故事**：作为 Skill 负责人，我需要看到失败的具体成因和修复层级，而不是只看到 prompt/生成失败。

- 当系统解析已确认报告时，系统应将原始结果信号与三元组归因分开保存。
- 当 Critic Agent 不能给出符合枚举的二级标签时，系统应拒绝该候选并说明原因。
- 当同一原因覆盖多个报告分组时，系统应语义归并候选但保留全部证据引用。

### R2：证据约束

**故事**：作为审核人，我需要知道 AI 为什么这样归因。

- 当 Critic Agent 提出归因时，系统应要求至少一条可定位证据。
- 当证据引用无法在当次 trace/报告中解析时，系统应将候选标为不可采纳。
- 当用户查看候选时，系统应展示证据摘要并允许定位到来源节点/报告行。

### R3：人工归因闸口

**故事**：作为审核人，我需要修正 AI 的归因，防止归因幻觉进入进化库。

- 当候选处于 `proposed` 状态时，系统不得用它生成正式补丁。
- 当审核人选择 Re-label 时，系统应允许同时修改一级类别、二级标签、修复层级与候选描述。
- 当审核人驳回候选时，系统应保留驳回结论供后续去重，不应删除记录。

### R4：定向候选补丁

**故事**：作为 Skill 负责人，我需要看到可直接审核的修改，而不是抽象建议。

- 当归因的修复层级为 Prompt 或 Skill SOP 时，系统应生成针对精确文件的最小 unified diff。
- 当修复层级为 Few-Shot 时，系统应生成由 Bad Case 与人工期望组成的正反例候选。
- 当修复层级为 Tool/Workflow 或 Knowledge/RAG 时，系统应在隔离试验副本中生成可执行补丁；只有通过评测与审批后才能替换正式资产。
- 当补丁扩大 Token、影响公共步骤或改动多文件时，系统应显式标记影响面与风险。

### R5：安全派生与本阶段回归

**故事**：作为发布负责人，我需要保证进化不破坏当前稳定版本。

- 当系统执行进化时，系统应从当次任务实际锁定的 Skill 精确版本派生不可变试验版。
- 当试验版本生成时，系统应保证当前 active 包的内容和指纹不变。
- 当本阶段重跑未通过或人工未确认时，系统不得允许发布候选版。
- 当本阶段重跑通过且人工确认 diff 后，系统应允许进入发布审批。

### R6：隔离变体与 A/B Mutation

**故事**：作为 Skill 负责人，我需要同时比较保守修复和结构优化，而不是只接受单一 AI 方案。

- 当已确认归因进入执行进化时，系统应从同一基线派生至少 A/B 两个隔离变体。
- 当生成 Candidate A 时，系统应以最小扰动方式补充约束、格式或示例。
- 当生成 Candidate B 时，系统应调用预置 `skill-creator` 重构步骤、分支、前置检查和兜底流。
- 当变体生成时，系统应为每个变体记录独立版本、补丁、基线、指纹、影响面和回滚点。
- 当 A/B 变体进入评测时，系统应使用相同输入分别重跑 Baseline/A/B，不得共享可变运行目录。
- 当人工选择胜出变体时，系统应保留未入选变体的试验记录，但不得将其发布到 Skill Hub。

### R7：全链路可追溯

**故事**：作为治理负责人，我需要从新版 Skill 反查到人工反馈和运行证据。

- 当候选版本派生时，系统应关联源 Skill 版本、原始产出、反馈报告、已确认归因、补丁与回归结果。
- 当用户查看进化历史时，系统应展示这条链路的状态、操作人和时间。

## 6. 非功能要求

- 幂等：同一输出 + 同一证据指纹 + 同一归因不得重复落库。
- 安全：候选阶段不得改变 active Skill 或全局共享资产。
- 隐私：证据展示需沿用项目权限，敏感 Payload 只存引用/摘要。
- 兼容：已有 `FailureAttribution.category` 不立即删除，允许历史记录以旧格式读取。
- 可观测：Critic、候选补丁、重跑、发布每一步必须有状态与失败原因。

## 7. 待确认口径

无。用户已确认：方案中未标注“后续阶段实现”的内容均在本期完成。
