# 审查规则

- 模糊表述：正常、正确、成功、无异常等词只有在缺少明确可观察标准时才是问题。
- 前置与数据：检查角色权限、环境配置、关键数据、唯一标识及会改变结果的上下文。
- 步骤可执行：入口、对象、动作、顺序和隐含操作应足以复现。
- 预期完整：不仅检查过程成功，还要检查落库、状态、下游、字段、数量、顺序、格式和持久化结果。
- 覆盖范围：按业务风险检查合法/非法、空值、边界、重复、权限、状态、并发及失败回滚。
- 一致性：明确比较双方、字段与规则，不能只写“数据一致”。
- 证据追溯：关键测试应保留足以复核的版本、环境、数据、截图、日志或原始文件。
- 可维护性：避免依赖口头知识和无法定位版本的“参考线上”“同以前”“按需求”。
- 同一根因尽量合并，避免低价值告警淹没关键风险。

## 跨任务与跨批次状态隔离

适用于短信、邮件、消息推送、支付、文件处理、批量任务等异步执行并由回调或状态报告更新结果的场景。

- 识别业务对象的完整关联范围：会议/任务标识、发送批次号、接收对象标识、渠道或运营商等。不能把手机号、账号等可跨任务复用的字段单独当作状态更新唯一条件。
- 当同一手机号、账号或其他接收对象同时存在于不同会议、任务或批次时，必须覆盖各批次产生不同结果的场景，例如一个失败、另一个成功。
- 必须验证每次回调只更新与其会议/任务/批次匹配的记录，其他批次的状态、时间、失败原因和重试次数保持不变。
- 至少覆盖正常顺序、逆序到达和重复回调；若系统声明支持并发，还应覆盖近同时回调。回调顺序不得改变最终归属。
- 不得把“任务 A 发送操作结束后再创建或发送任务 B”视为充分隔离。发送操作结束不代表运营商或下游状态报告已经返回；必须主动延迟 A 的回调，待 B 的记录入库后再返回 A 的状态，以验证迟到回调不会命中 B。
- 渠道存在差异时，应分别覆盖异步状态报告渠道与同步/无状态报告渠道，并验证问题只受真实关联逻辑影响。某个渠道未复现不能证明其他渠道安全。
- 步骤与预期应成对：发送或构造某批次回调后，立即核对该批次的目标记录，同时核对共享手机号在另一批次中的记录未被串改。
- 若需求未明确状态关联键，标记为“待业务确认”，建议确认是否至少包含任务/会议标识与批次号；不得擅自认定具体数据库字段。
- 缺少上述隔离验证时，通常定为高风险：串改可能让失败记录显示成功、成功记录显示失败，直接影响业务结果判断。

推荐回归用例结构：

- 前置：任务 A 与任务 B 使用相同发送渠道，包含同一接收对象 X，但分别属于不同批次 A1、B1；两条记录初始均为待发送。
- 步骤 1：触发 A1 发送，但暂不返回 A1 状态报告；记录 A1 的任务标识、批次号和渠道流水号。
- 预期 1：A1 已生成独立发送记录并保持处理中或待回执状态，尚未影响其他任务。
- 步骤 2：创建并触发 B1 发送，使共享对象 X 的 B1 记录先入库。
- 预期 2：B1 生成独立发送记录，关联标识与 A1 不混用。
- 步骤 3：在 B1 入库后返回 A1 失败回调，再返回 B1 成功回调；另行覆盖相反顺序、重复回调和近同时回调。
- 预期 3：A1 仅更新为失败并记录其失败原因；B1 仅更新为成功。两条记录的状态、更新时间、失败原因和重试信息互不污染，查询接口与页面展示一致。
